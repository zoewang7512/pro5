## 問題

設計師目前完全看不到顧客透過前台送出的預約——`app/admin/page.tsx` 只是登入後的暫代頁面，
沒有任何預約資料的呈現或操作介面。顧客送出的 `pending` 預約進了資料庫後，設計師只能直接查
Supabase dashboard 才看得到，沒有任何在後台「標記完成」「取消」「改期」的方式。

## 使用者

已登入且通過 `is_admin()` 驗證的唯一設計師帳號（後台，桌面／平板為主，對應
`ai/context/project-map.md` 的「設計師」使用者）。

## 目標

- 設計師登入後台後，能用日曆或列表檢視所有預約（含顧客姓名／服務／時段／狀態）。
- 設計師能把某筆預約標記為「已完成」。
- 設計師能取消某筆預約。
- 設計師能變更某筆預約的日期或時段（改期），且新時段仍受既有的時段衝突防護保護
  （不能改到與其他預約重疊的時段）。
- 沿用 Epic 0 S5 已核准的變體 C「側邊欄＋日曆優先」版型（見
  [`mockup-decision-設計師後台.md`](../專案設置/mockup-decision-設計師後台.md)），新增
  Sidebar 導覽元件與週曆格狀檢視元件並登記回 `ai/context/design-system.md` 的 S4 元件庫
  inventory。

## 非目標

- 服務項目的新增／編輯／下架 UI——留給「服務項目管理」Epic；本 Epic 側邊欄會保留「服務設定」
  導覽項目位置（沿用 S5 mockup 的三分頁結構），但內容頁面不在本 Epic 實作範圍。
- 營業時間／公休日／緩衝時間的設定 UI——留給「營業時間與可預約時段管理」Epic；同上，側邊欄
  保留「營業時間」導覽項目位置，內容頁面不在本 Epic 實作範圍。
- 取消／改期時通知顧客（email／簡訊）——留給「Email 通知與提醒」Epic；本 Epic 的取消／改期
  操作只更新資料庫，不觸發任何對外通知。
- 設計師手動「新增」一筆全新預約（例如電話預約由設計師直接輸入）——不在本 Epic 4 個 User
  Story 的範圍內，若有需要應另立 User Story／任務卡，避免本 Epic 範圍模糊擴大。
- 顧客資料的獨立管理頁面（顧客清單、合併重複顧客等）——留給「顧客資料管理」Epic；本 Epic
  的日曆／列表只呈現預約本身關聯的顧客姓名／電話／email，不提供獨立的顧客管理介面。
- 操作歷史／稽核軌跡（誰在何時把預約改成什麼狀態）——留給「稽核紀錄」Epic。
- 儀表板統計數字（本週預約數、營收等）——留給「儀表板與報表」Epic。
- 進階篩選（依顧客姓名／電話全文搜尋預約）——本階段僅提供日期／週次切換與狀態篩選，全文
  搜尋留待有實際需求時再處理，記錄為已知限制。

## 使用者故事（User Stories）

| 故事 | 身為／我想要／以便 | 驗收標準 |
|---|---|---|
| 查看預約列表／日曆 | 身為設計師，我想要用日曆或列表檢視所有預約，以便掌握每天／每週的工作安排 | 週曆為預設檢視，可切換列表檢視；兩種檢視皆顯示顧客姓名／服務／時段／狀態；可切換週次；載入中與無預約的空狀態皆有對應畫面 |
| 標記預約完成 | 身為設計師，我想要把已服務完的預約標記為完成，以便追蹤哪些預約還沒處理 | 從日曆或列表點選預約可標記為 `completed`；操作後畫面即時反映新狀態；只有 `pending`／`confirmed` 狀態的預約能被標記完成 |
| 取消預約 | 身為設計師，我想要取消顧客的預約，以便處理顧客電話告知取消或無法履約的情況 | 取消前需二次確認（沿用 `ConfirmDialog`）；取消後狀態變成 `cancelled`，該時段立即釋出（可再被其他顧客預約，因為 `cancelled` 不在 exclusion constraint 的鎖定狀態清單內）；已取消或已完成的預約不能再被取消 |
| 改期預約 | 身為設計師，我想要直接變更某筆預約的日期或時段，以便處理顧客電話告知的改期需求，不用先取消再重建 | 改期表單可選新日期／時段；新時段與其他既有預約（不分服務）重疊時，操作被資料庫層 exclusion constraint 擋下並顯示對應錯誤訊息，不影響原預約；改期成功後日曆／列表即時反映新時段；已取消或已完成的預約不能再改期 |

## 使用者旅程

```text
身為已登入的設計師
我想要打開後台就看到本週的預約分佈，點一筆預約就能標記完成、取消，或改到別的時段
以便不用切到 Supabase dashboard 或用電話跟顧客反覆確認，就能把每天的預約處理完
```

## 功能需求

- WHEN 設計師登入後台 THE SYSTEM SHALL 預設顯示本週的預約週曆檢視（沿用 S5 變體 C
  版型），並提供切換到列表檢視的選項。
- WHEN 設計師在週曆或列表檢視中瀏覽 THE SYSTEM SHALL 顯示每筆預約的顧客姓名、服務名稱、
  時段（起訖時間）、目前狀態（`pending`／`confirmed`／`completed`／`cancelled`，以顏色或
  標籤區分）。
- WHEN 設計師切換週次（上一週／下一週／回到本週） THE SYSTEM SHALL 重新查詢並顯示對應週次
  的預約，不需要重新整理整頁。
- WHEN 設計師點選一筆狀態為 `pending` 或 `confirmed` 的預約並選擇「標記完成」 THE SYSTEM
  SHALL 把該預約狀態更新為 `completed`，並在畫面上即時反映。
- WHEN 設計師點選一筆非 `cancelled`／`completed` 的預約並選擇「取消」 THE SYSTEM SHALL
  先顯示二次確認對話框，確認後才把狀態更新為 `cancelled`；取消後的時段因不在 exclusion
  constraint 鎖定的狀態清單內，會自動釋出供其他預約使用。
- WHEN 設計師點選一筆非 `cancelled`／`completed` 的預約並選擇「改期」、選定新的日期與時段
  後送出 THE SYSTEM SHALL 嘗試把該預約的 `start_at`／`end_at` 更新為新時段；若新時段與其他
  預約時段重疊，THE SYSTEM SHALL 拒絕更新（由資料庫層 exclusion constraint 擋下）、保持原
  時段不變，並顯示「這個時段已被其他預約占用」之類的錯誤訊息。
- WHEN 設計師嘗試對已經是 `cancelled` 或 `completed` 的預約做「標記完成」「取消」「改期」
  任何操作 THE SYSTEM SHALL 在畫面上就不提供對應操作入口（不是等送出才報錯）。
- WHEN 非管理者身分（未登入或非 `is_admin()`）嘗試存取本後台頁面 THE SYSTEM SHALL 沿用
  TASK-003 既有的 `proxy.ts` 與頁面內 `is_admin()` 二次確認機制導回登入頁，不在本 Epic
  重做這段邏輯。

## 畫面

依 Epic 0 S5 已核准的變體 C「側邊欄＋日曆優先」（見
[`screen-spec-設計師後台核心畫面.md`](../專案設置/screen-spec-設計師後台核心畫面.md)），本
Epic 聚焦其中的「預約週曆／列表」畫面：

| 畫面 | 狀態 | 備註 |
|---|---|---|
| 預約週曆（預設） | 預設、載入中、空狀態（本週無預約）、行動裝置版（非本階段重點，桌面／平板優先） | 週曆網格，可切換到列表 |
| 預約列表 | 預設、載入中、空狀態 | 表格呈現，同一組資料的另一種檢視 |
| 標記完成／取消 | 確認中（`ConfirmDialog`）、送出中（`loading`）、成功（Toast）、失敗（Toast） | 沿用 S4 既有元件 |
| 改期 | 表單預設、驗證錯誤（未選時段）、送出中、成功（Toast）、失敗（`SLOT_CONFLICT` 類錯誤 Toast） | 表單樣式沿用既有慣例 |
| Sidebar 導覽 | 「預約」使用中狀態、其餘兩項（服務設定／營業時間）顯示但暫不可用或連結到待實作頁面 | 新元件，需登記回 S4 inventory |

## 資料與 API

- 輸入：讀取 `appointments`（含關聯的 `services.name`／`customers` 姓名電話）：設計師身分
  已通過 `authenticated` + `is_admin()` RLS policy（TASK-003 既有的「admin full access to
  appointments」），可直接用 Supabase client 查詢，不需要新的 RPC。
- 輸出：
  - 標記完成／取消：直接對 `appointments` 做 `update status = ...`，走既有的 admin RLS
    policy（`with check (is_admin())`），不需要新 RPC。
  - 改期：直接對 `appointments` 做 `update start_at, end_at = ...`；時段衝突由既有的
    `appointments_no_overlap` exclusion constraint 在資料庫層擋下（`update` 違反 exclusion
    constraint 時 Postgres 回傳 `23P01 exclusion_violation`），前端需捕捉並轉成對使用者友善
    的錯誤訊息，比照顧客端 `create_appointment` 的錯誤處理風格（不直接把原始 Postgres 錯誤
    訊息顯示給使用者）。
  - 若實作規劃階段發現直接 `update` 不足以應付某些邊界（例如需要在同一交易內做額外驗證），
    改採 `SECURITY DEFINER` RPC 是可接受的替代方案，屆時在對應任務卡記錄理由。
- 驗證：改期送出的新時段須為合法的未來時間（比照顧客端至少不能是過去時間；設計師是內部
  使用者，可以不套用「提前 1 小時」與「90 天視野」這兩條給顧客的防濫用限制——這兩條規則
  是為了防止 anon 濫用，不適用於已登入的設計師）。
- 錯誤：時段衝突（改期時對應 Postgres exclusion constraint 違反）、更新失敗（未預期資料庫
  錯誤，顯示通用錯誤訊息）。

## 安全性與隱私

- 身分驗證：沿用 Supabase Auth + TASK-003 既有的唯一設計師帳號機制，本 Epic 不新增登入
  相關邏輯。
- 權限：所有讀寫皆透過已登入 `authenticated` 角色 + `is_admin()` RLS policy，不新增任何
  anon 可觸及的介面或 RPC；`proxy.ts` 沿用既有的路由層第一道門。
- 敏感資料：預約列表會顯示顧客姓名／電話／email——這些資料只呈現給已驗證的設計師，不記錄
  於 client-side log；沿用顧客端既有的「應用層不主動記錄個資」原則。
- 濫用情境：唯一設計師帳號本身即代表最高權限，本 Epic 不另外做操作層級的細粒度權限（例如
  未來若有多個員工帳號，需要另外設計角色權限，目前系統假設只有一個設計師帳號，屬既有假設，
  不在本 Epic 重新討論）。

## 驗收標準

- 設計師登入後台，預設看到本週預約週曆，可切換到列表檢視，兩者資料一致。
- 標記完成／取消／改期三個操作皆可從畫面完成，且皆有二次確認（取消）或表單驗證（改期）、
  送出中 loading、成功／失敗 Toast。
- 改期到與既有預約重疊的時段會被資料庫層擋下，不會建立出兩筆重疊的預約；改期到相鄰但不
  重疊的時段應該成功。
- 取消後的時段能被驗證為「已釋出」（例如可以再次被 `get_available_slots` 或另一筆改期／
  新預約使用，但這屬於「顧客預約流程」既有 RPC 的既有邏輯，本 Epic 只需驗證取消後的狀態
  正確寫入 `cancelled`）。
- 非管理者或未登入身分無法存取本後台頁面（沿用既有機制）。
- `npx tsc --noEmit`／`npm run lint`／`npm run build`／`npm test`（含新增單元測試）皆通過。

## 驗證計畫

- 單元測試：預約狀態轉換規則的純函式邏輯（例如「這個狀態的預約能不能標記完成／取消／
  改期」的判斷）、日期／週次切換的純函式邏輯（可能可以沿用或比照顧客端
  `lib/booking/date-range.ts` 的寫法）。
- 整合測試：對真實 Supabase 專案驗證 admin 角色的 update 權限邊界（含改期時 exclusion
  constraint 正確擋下衝突、相鄰時段可共存）；比照 `tests/rls.integration.test.ts` 與
  `tests/booking.integration.test.ts` 的既有模式。
- E2E／視覺：Browser 工具在桌面／平板尺寸下走查完整流程（週曆→列表切換→標記完成→取消
  →改期），比對 S5 mockup 變體 C 與本文件「畫面」狀態表。
- 手動：至少驗證一次「改期到已被其他預約占用的時段」會被正確擋下且原預約不受影響。
