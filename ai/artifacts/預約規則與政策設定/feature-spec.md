# 功能規格書

## Metadata

- 功能：預約規則與政策設定（對應 `tools/kanban/epics.json` 已登記的同名 Epic）
- 負責人：待指定
- 狀態：草稿（待人工核准）
- 風險等級：高（「設定最短提前預約時間」需要修改 `create_appointment`——顧客端唯一的
  預約寫入路徑——把目前寫死的 1 小時提前量改為從設定值讀取，任何邏輯錯誤可能導致合法
  預約被誤擋或非法預約被放行，需架構、安全性、測試三方審查）
- 已與人工確認的範圍決策：
  - 「設定最短提前預約時間」的預設值維持與現行程式碼一致的 **1 小時**，設計師之後可自行
    調整；不因本批次上線而意外改變既有顧客預約行為。
  - 「設定可取消／改期時限」本批次**只做設定與顯示**，不強制執行——目前顧客沒有自助
    取消／改期功能（屬於未來「顧客自助查詢／取消預約」Epic），設計師後台手動取消／改期
    （既有「預約管理後台」Epic）也不受此設定限制；本批次先讓設計師設定數值、顧客端看到
    政策說明文字，實際強制執行邏輯留給該未來 Epic 實作時接上。

## 問題

- `create_appointment` RPC 目前把「最短提前 1 小時可預約」與「最遠可預約 90 天」都寫死在
  SQL 裡（`supabase/migrations/0002_booking_flow.sql` 第 209 行），設計師無法自行調整
  最短提前預約時間，任何調整都需要工程人員改程式碼並重新部署 migration。
- 目前完全沒有「可取消／改期時限」的設定或顧客可見的政策說明，顧客在預約流程中不知道
  自己之後能不能取消或改期、有沒有時間限制。

## 使用者

- 設計師（後台唯一登入帳號，經 `is_admin()` 驗證）：直接使用者，設定最短提前預約時間、
  可取消／改期時限。
- 顧客（前台，未登入）：間接受影響——預約流程中會看到提前預約與取消／改期規則的說明；
  可預約時段的計算會反映設計師設定的最短提前預約時間。

## 目標

- 讓設計師能在後台設定「最短提前預約時間」，`create_appointment` 與 `get_available_slots`
  依此設定值計算，取代目前寫死的 1 小時。
- 讓設計師能在後台設定「可取消／改期時限」數值（僅儲存與顯示，見範圍決策）。
- 讓顧客在預約流程中看到目前的提前預約與取消／改期政策說明文字。

## 非目標

- **最遠可預約天數（視野上限，目前寫死 90 天）的可設定化**——需求只提出「最短提前預約
  時間」，視野上限維持現行寫死值，不在本批次範圍。
- **可取消／改期時限的強制執行**——已與人工確認，本批次只做設定與顯示；顧客自助取消／
  改期功能屬於「顧客自助查詢／取消預約」Epic（尚未開始），該 Epic 實作時需回頭接上這個
  設定值做實際的時限檢查。
- **設計師後台手動取消／改期受可取消時限限制**——「預約管理後台」Epic 的既有手動取消／
  改期功能是設計師的管理權限操作，不受顧客端政策時限約束，本批次不新增此限制。
- **政策說明文字的多語系或富文本編輯**——政策說明由固定文案模板套入設定的數值組成（例如
  「請於預約時段前 {N} 小時完成預約」），不提供自由文字欄位或 WYSIWYG 編輯，維持純中文。
- **緩衝時間（`buffer_minutes`）等其他預約規則**——已由「營業時間與可預約時段管理」Epic
  管理，不在本批次範圍。

## 使用者故事（User Stories）

| 故事 | 身為／我想要／以便 | 驗收標準 |
|---|---|---|
| 設定最短提前預約時間 | 身為設計師，我想要設定顧客最晚需提前多久預約，以便有足夠準備時間，避免臨時被預約打亂排程 | 後台可設定最短提前預約時間（小時，預設 1 小時）；設定後 `get_available_slots` 不再顯示低於此時間的時段；`create_appointment` 對低於此時間的請求拒絕並回傳既有錯誤碼；設定值有基本範圍驗證 |
| 設定可取消／改期時限 | 身為設計師，我想要設定顧客可免費取消或改期的時限，以便未來顧客自助取消/改期功能上線時有規則可循 | 後台可設定可取消／改期時限（小時）；設定值儲存成功；顧客前台的政策說明文字正確反映此數值；本批次不強制執行實際取消/改期限制（見「非目標」） |
| 顧客端顯示預約政策說明 | 身為顧客，我想要在預約流程中看到提前預約與取消/改期的規則說明，以便了解預約後的彈性與限制 | 顧客預約流程中有政策說明區塊，文字依設計師設定的兩個數值動態組成；設計師未設定（維持預設）時仍顯示合理文案，不出現空白或錯誤 |

## 使用者旅程

```text
身為設計師，
我想把最短提前預約時間從預設的 1 小時改成 3 小時，讓我有更充足的準備時間，
以便不會臨時被預約打亂排程。

我登入後台，點進新的「預約規則」頁，看到目前的最短提前預約時間（1 小時）與可取消/改期
時限（尚未設定）。我把最短提前預約時間改成 3 小時、可取消/改期時限設成 24 小時，點儲存。
我切到顧客前台，選擇服務後看到時段選擇畫面，3 小時內的時段已經不再出現於可選清單；畫面
下方的政策說明也更新為「請於預約時段前 3 小時完成預約」「預約時段前 24 小時內可免費取消
或改期」。
```

## 功能需求

使用可測試的語言撰寫。

- WHEN 設計師在「預約規則」頁設定最短提前預約時間（小時）並送出 THE SYSTEM SHALL 驗證
  數值為大於 0 的整數（合理上限，例如不超過 720 小時／30 天，避免設定值荒謬導致顧客
  完全無法預約），通過後寫入 `booking_policy` 並顯示成功提示。
- WHEN 設計師在「預約規則」頁設定可取消／改期時限（小時）並送出 THE SYSTEM SHALL 驗證
  數值為大於等於 0 的整數，通過後寫入 `booking_policy` 並顯示成功提示。
- WHEN 顧客端呼叫 `get_available_slots` THE SYSTEM SHALL 依 `booking_policy` 目前設定的
  最短提前預約時間計算可選時段，不顯示低於此時間門檻的時段（取代現行寫死的 1 小時）。
- WHEN 顧客端呼叫 `create_appointment` 且 `p_start_at` 低於目前設定的最短提前預約時間
  THE SYSTEM SHALL 拒絕該請求，沿用既有 `VALIDATION_ERROR` 錯誤碼與訊息格式（不新增
  錯誤碼，比照 TASK-028 的既有決策：公休日檢查沿用既有錯誤碼的相同精神）。
- WHEN 顧客瀏覽預約流程 THE SYSTEM SHALL 顯示政策說明文字，依目前 `booking_policy` 的
  兩個設定值組成（例如「請於預約時段前 {N} 小時完成預約」「預約時段前 {M} 小時內可免費
  取消或改期」）；可取消／改期時限未設定時，該句文案不顯示或顯示「詳情請洽店家」等
  合理預設，不顯示空白或錯誤數值。
- WHEN 非管理員（含 anon 與已登入但非 `is_admin()` 的 authenticated 使用者）嘗試寫入
  `booking_policy` THE SYSTEM SHALL 拒絕該操作。

## 資料與 API

- 輸入：
  - `booking_policy` 新資料表（單例，僅允許一列，比照本專案既有「小型設定表」模式，如
    `store_settings`／`business_hours` 的既有做法）：
    - `min_lead_time_hours int not null default 1 check (min_lead_time_hours > 0 and
      min_lead_time_hours <= 720)`（最短提前預約時間，小時；預設 1，對齊現行寫死值）
    - `cancel_window_hours int check (cancel_window_hours >= 0)`（可取消／改期時限，
      小時；選填，`null` 代表尚未設定）
    - `updated_at timestamptz not null default now()`
  - `create_appointment`／`get_available_slots` 兩支既有 RPC 修改：讀取
    `booking_policy.min_lead_time_hours`（取代寫死的 `interval '1 hour'`），最遠視野
    上限（90 天）維持不變。
- 輸出：
  - 前台／後台皆透過薄封裝函式讀取 `booking_policy` 單一列（若不存在則視為預設值
    `min_lead_time_hours = 1`／`cancel_window_hours = null`，比照 `store_settings` 的
    既有降級模式，但實務上本表會透過 migration seed 保證恆有 1 列，比照 `store_settings`
    與 `business_hours` 的既有做法，不應出現零列情境）。
- 驗證：
  - 前端與資料庫（`check` constraint）皆驗證最短提前預約時間範圍（1～720 小時）、可
    取消／改期時限（≥ 0 或空值）。
- 錯誤：
  - 資料庫錯誤時前端顯示通用友善訊息，不外洩原始錯誤內容，比照既有慣例。

## 安全性與隱私

- 身分驗證：沿用既有 `is_admin()` + authenticated 邊界。
- 權限：`booking_policy` 的 RLS policy 比照 `business_hours`／`store_settings`——
  anon／authenticated 皆可讀（供顧客端頁面與 `get_available_slots`／`create_appointment`
  RPC 使用），只有 `is_admin()` 可寫。
- 敏感資料：本 Epic 涉及的欄位（時數設定）皆為店家營運規則，非個人隱私資料。
- 濫用情境：
  - `create_appointment`／`get_available_slots` 的提前量檢查修改需要與既有的公休日
    （TASK-024／028）、緩衝時間（TASK-022）檢查邏輯正確共存，不互相覆蓋或短路，需在
    整合測試中逐一驗證各項規則同時生效時的行為（例如同時設定較長的提前時間與公休日，
    兩種限制應該都要生效，不是後加的邏輯覆蓋先前的檢查）。
  - 非管理員寫入 `booking_policy` 需在整合測試中驗證皆被拒絕。

## 驗收標準

- 設計師可在後台「預約規則」頁設定最短提前預約時間（1～720 小時）與可取消／改期時限
  （≥ 0 小時或留空）。
- `get_available_slots`／`create_appointment` 正確依設定的最短提前預約時間計算/驗證，
  取代現行寫死的 1 小時；未設定時維持原本 1 小時的既有行為（無回歸）。
- 顧客前台正確顯示依設定值組成的政策說明文字，未設定可取消時限時顯示合理預設，不顯示
  空白或錯誤。
- 非管理員無法寫入 `booking_policy`。
- 既有測試（`test:rls`／`test:booking`／`test:admin-booking`／`test:business-hours`／
  `test:store-settings`／`test:services`）重跑無回歸。

## 驗證計畫

- 單元測試：最短提前預約時間／可取消時限欄位的前端驗證邏輯（純函式）；政策說明文案
  組成函式（依數值產生對應文字，含未設定時的降級文案）。
- 整合測試：對真實 Supabase 專案驗證 `booking_policy` 的 RLS 邊界（anon／非管理員
  authenticated 只能讀、寫入被拒；`is_admin()` 可讀寫）；`get_available_slots`／
  `create_appointment` 對調整後的最短提前預約時間的正確回應（含與既有公休日／緩衝時間
  規則同時生效的組合案例）；驗證後還原測試資料。
- E2E：Browser 工具桌面尺寸走查（後台設定兩個數值並儲存、切到顧客前台確認可選時段與
  政策說明文字皆正確反映）。
- 視覺：預約規則頁與顧客前台政策說明區塊的畫面狀態表，比照 `design-craft` 檢查表。
- 手動：確認修改 `create_appointment`／`get_available_slots` 後，既有正常預約流程（在
  提前時間門檻之外的時段）不受影響，仍可正常完成預約。
