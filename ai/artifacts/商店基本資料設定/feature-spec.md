# 功能規格書

## Metadata

- 功能：商店基本資料設定（對應 `tools/kanban/epics.json` 已登記的同名 Epic）
- 負責人：待指定
- 狀態：人工已核准（2026-08-07）
- 風險等級：中（首次在本專案引入 Supabase Storage 檔案上傳；新增 `store_settings` 單例設定表與對應
  RLS policy；顧客前台首頁新增品牌顯示區塊，屬於既有頁面的版面異動，不影響既有預約流程邏輯）
- 已與人工確認的範圍決策：
  - 店名／地址／電話／簡介：本批次為「後台設定＋前台完整顯示」（不是只做後台）。
  - Logo／封面圖：本批次為「前台頁首 Logo＋首頁 Banner 封面圖」（不是只做後台上傳預覽）。

## 問題

- 目前顧客前台（`app/page.tsx` → `BookingFlow.tsx`）完全沒有任何品牌／店家資訊顯示區塊，畫面
  最上方只有寫死的「預約」標題，顧客看不到店名、地址、電話、簡介，也看不到任何 Logo 或封面圖。
- 後台 Sidebar（`AdminShell.tsx`）目前也是寫死「理髮廳後台」固定文字，沒有店家資訊來源。
- 設計師沒有任何介面可以設定或更新這些基本聯絡資訊與品牌素材，全部需要工程人員手動改程式碼
  才能調整，不符合「設計師自行管理店家資訊」的產品目標。
- 本專案目前完全沒有使用過 Supabase Storage（檔案上傳），需要在本批次首次引入。

## 使用者

- 設計師（後台唯一登入帳號，經 `is_admin()` 驗證）：直接使用者，設定與更新店名、地址、電話、
  簡介、Logo、封面圖。
- 顧客（前台，未登入）：間接受影響——前台首頁會顯示設計師設定的店名、簡介、地址、電話、Logo、
  封面圖 Banner。

## 目標

- 讓設計師能在後台一個畫面內編輯店名、地址、電話、簡介，並看到目前已設定的內容。
- 讓設計師能在後台上傳／更換 Logo 與封面圖，並即時看到預覽。
- 顧客前台首頁正確顯示已設定的店名（頁首）、簡介（首頁內文）、地址與電話（聯絡資訊區塊）、
  Logo（頁首）、封面圖（首頁 Banner）。
- 尚未設定任何資料時（全新專案／欄位留空），前台與後台都要有合理的預設／空狀態呈現，不出現
  破版或錯誤畫面。

## 非目標

- **多分店／多地址管理**——沿用本專案「單一理髮廳」的既有假設，`store_settings` 是單例（僅一列）
  設定，不支援多筆。
- **簡介欄位的富文本格式（粗體、超連結、圖片內嵌等）**——只支援純文字（可含換行），不做
  Markdown／WYSIWYG 編輯器。
- **圖片裁切／編輯工具**——設計師上傳的圖片直接使用，不提供裁切、旋轉、濾鏡等編輯功能；圖片
  比例建議寫在表單說明文字，不做強制裁切。
- **多語系內容**——維持全站繁體中文，不做店名/簡介的多語言版本。
- **異動歷史／稽核紀錄**——沿用既有規劃，稽核紀錄是獨立的未來 Epic（見 `epics.json`「稽核
  紀錄」），本批次的商店設定變更不特別記錄異動歷史，只保留 `updated_at` 供除錯參考。
- **社群媒體連結、營業時間顯示**——營業時間顯示屬於「營業時間與可預約時段管理」Epic 既有範圍
  （目前前台尚未顯示營業時間，非本 Epic 處理），社群連結未在使用者故事中提出，不在本批次範圍。
- **CDN／圖片轉檔最佳化管線**——直接使用 Supabase Storage public URL，不額外接圖片處理服務；
  僅在前端套用瀏覽器原生 `loading="lazy"`／MUI 既有圖片顯示模式，不做進階效能優化。
- **後台 Sidebar 標題（「理髮廳後台」）是否改用設定的店名**——版面細節留給 UI Mockup 關卡決定，
  不在功能規格書預先鎖定，避免限制畫面設計。

## 功能需求

使用可測試的語言撰寫。

- WHEN 設計師在商店設定頁編輯店名／地址／電話／簡介並送出儲存 THE SYSTEM SHALL 驗證店名不可為
  空白，其餘三欄位可為空，通過驗證後寫入 `store_settings` 並顯示成功提示；驗證失敗時阻擋送出並
  標示錯誤欄位。
- WHEN 設計師上傳 Logo 或封面圖檔案 THE SYSTEM SHALL 驗證檔案格式（jpg／png／webp）與檔案大小
  上限（5MB），通過後上傳至 Supabase Storage 並更新 `store_settings` 對應的圖片 URL 欄位、顯示
  上傳後的預覽；格式或大小不符時顯示對應錯誤訊息，不影響其他已儲存的設定。
- WHEN 設計師更換既有的 Logo 或封面圖 THE SYSTEM SHALL 以新檔案取代舊圖，前台顯示同步更新為新
  圖片（透過內含檔案雜湊或時間戳記的儲存路徑／檔名，避免瀏覽器快取顯示舊圖）。
- WHEN 顧客瀏覽前台首頁 THE SYSTEM SHALL 於頁首顯示目前設定的 Logo 與店名、於首頁顯示簡介與
  封面圖 Banner、於聯絡資訊區塊顯示地址與電話；任一欄位或圖片尚未設定時，該區塊呈現對應的預設
  狀態（例如無 Logo 時只顯示店名文字、無封面圖時不渲染 Banner 區塊、無地址/電話時不顯示對應
  列），不得顯示錯誤訊息或破版版面。
- WHEN `store_settings` 尚無任何資料列（全新環境、尚未有人儲存過） THE SYSTEM SHALL 前台以全部
  欄位視為未設定的方式呈現（比照上一條的預設狀態邏輯），後台商店設定頁顯示空白表單而非錯誤。
- WHEN 非管理員（含 anon 與已登入但非 `is_admin()` 的 authenticated 使用者）嘗試寫入
  `store_settings` 或上傳至 Storage bucket THE SYSTEM SHALL 拒絕該操作，沿用既有 RLS／
  `is_admin()` 邊界模式。

## 資料與 API

- 輸入：
  - `store_settings` 新資料表（單例，僅允許一列，比照本專案既有「小型設定表」模式，例如以
    `id boolean primary key default true` 搭配 check constraint 限制只能有一列，或等效做法，
    細節留給架構規劃階段）：
    - `name text not null default ''`（店名；寫入時後端驗證非空白）
    - `address text`（選填）
    - `phone text`（選填；基本格式驗證，例如允許數字／`-`／`+`／空格，長度上限）
    - `description text`（選填；長度上限，例如 500 字，避免前台版面被過長文字撐爆）
    - `logo_url text`（選填，Supabase Storage public URL）
    - `cover_image_url text`（選填，Supabase Storage public URL）
    - `updated_at timestamptz not null default now()`
  - Supabase Storage：新增 public bucket（例如 `store-assets`），只存放 Logo／封面圖，檔名採
    固定路徑（例如 `logo`／`cover`＋副檔名＋雜湊或時間戳記後綴，不使用使用者原始檔名，避免路徑
    穿越與檔名衝突）。
- 輸出：
  - 前台／後台皆透過薄封裝函式讀取 `store_settings` 單一列（若不存在則視為全部欄位為預設值，
    比照功能需求最後一條）。
- 驗證：
  - 前端與後端（RLS／或伺服器端函式）皆驗證：店名非空白、電話基本格式、簡介長度上限、圖片
    格式（jpg／png／webp）與大小上限（5MB）。伺服器端驗證為最終防線，前端驗證只是體驗優化。
- 錯誤：
  - 資料庫或 Storage 錯誤時前端顯示通用友善訊息，不外洩原始錯誤內容，比照既有慣例
    （`lib/booking/error-messages.ts`／`lib/admin/` 既有錯誤處理模式）。

## 安全性與隱私

- 身分驗證：沿用既有 `is_admin()` + authenticated 邊界。
- 權限：`store_settings` 的 RLS policy 比照 `business_hours`／`closed_dates`——anon／
  authenticated 皆可讀（供顧客端頁面使用），只有 `is_admin()` 可寫。Storage bucket 政策同樣
  只允許 `is_admin()` 寫入，公開讀取（供前台顯示圖片，不需要簽章 URL）。
- 敏感資料：本 Epic 涉及的欄位（店名、地址、電話、簡介、圖片）皆為店家公開資訊，非個人隱私
  資料，公開讀取無隱私疑慮；電話為店家客服電話，不是顧客個資，與 `customers` 表的顧客電話是
  不同性質的資料，不比照顧客個資的存取限制。
- 濫用情境：
  - 檔案上傳需檢查 MIME type 與副檔名一致性、大小上限，避免上傳惡意檔案或超大檔案；儲存路徑
    使用固定命名而非使用者輸入的檔名，避免路徑穿越。
  - 簡介欄位為使用者輸入的自由文字，前台渲染時需避免 XSS（沿用既有 React 預設跳脫，不使用
    `dangerouslySetInnerHTML`）。
  - 非管理員（anon／非管理員 authenticated）寫入 `store_settings` 或上傳 Storage 皆須被拒絕，
    需在整合測試中驗證（比照既有 `test:business-hours` 對 RLS 邊界的驗證模式）。

## 驗收標準

- 設計師可在後台「商店設定」頁編輯並儲存店名（必填）、地址、電話、簡介（皆選填）。
- 設計師可在後台上傳／更換 Logo 與封面圖，有格式與大小驗證與錯誤提示，成功後有預覽。
- 顧客前台首頁正確顯示已設定的店名、簡介、地址、電話、Logo、封面圖；未設定的欄位／圖片呈現
  合理預設狀態，不破版、不顯示錯誤。
- 非管理員（anon／非管理員 authenticated）無法寫入 `store_settings` 或上傳至 Storage bucket。
- 既有測試（`test:rls`／`test:booking`／`test:admin-booking`／`test:business-hours`）重跑無
  回歸；顧客前台既有預約流程互動不受新增品牌顯示區塊影響。

## 驗證計畫

- 單元測試：店名／電話／簡介欄位的前端驗證邏輯（純函式）；圖片格式／大小驗證邏輯（純函式）；
  `store_settings` 讀取結果轉換為前台顯示用資料的邏輯（含「欄位未設定」的預設狀態計算）。
- 整合測試：對真實 Supabase 專案驗證 `store_settings` 的 RLS 邊界（anon／非管理員 authenticated
  只能讀、寫入被拒；`is_admin()` 可讀寫）；Storage bucket 的上傳權限邊界（比照同一模式）；讀取
  API 對「尚無資料列」情境的正確降級行為。
- E2E：Browser 工具桌面尺寸走查（後台編輯文字欄位並儲存、上傳並更換 Logo／封面圖、前台首頁
  對照顯示結果）。
- 視覺：後台商店設定頁與前台品牌顯示區塊的畫面狀態表，涵蓋預設／編輯中／儲存中／成功／錯誤／
  空狀態（前台部分／全部欄位未設定），比照 `design-craft` 檢查表。
- 手動：確認圖片更換後前台不會因瀏覽器快取顯示舊圖。
