# 畫面規格

## Metadata

- 功能：商店基本資料設定
- 畫面：商店設定（後台新頁面，暫定 `/admin/store-settings`）
- 狀態：mockup 已核准（變體 B：分卡片，各自獨立動作，見
  [`mockup-decision-商店設定.md`](mockup-decision-商店設定.md)），待實作，需先新做並登記圖片
  上傳元件回 S4 inventory

## 目的

讓設計師檢視並編輯店家的店名、地址、電話、簡介，以及上傳／更換 Logo 與首頁封面圖，取代目前
完全沒有介面、只能由工程人員手動改程式碼或資料庫的現況。

## 版面配置

- 主要區域：文字資訊表單（店名／地址／電話／簡介）。
- 次要區域：品牌圖片區塊（Logo 上傳／預覽、封面圖上傳／預覽）。
- 導覽：既有 Sidebar 新增「商店設定」項目（`href: /admin/store-settings`），比照「營業時間」
  項目從 `disabled` 改為可點擊並標記 active 的既有模式。
- 動作：依選定變體而定——變體 A 為單一「儲存」按鈕統一送出文字與圖片；變體 B 為「基本資訊」
  與「品牌圖片」各自獨立的動作（文字有自己的儲存按鈕，圖片選檔即自動上傳，無需額外按儲存）。

## 狀態

| 狀態 | 必要行為 | 空狀態／錯誤文案 | 驗證方式 |
|---|---|---|---|
| 載入中 | 顯示骨架屏（比照既有 `Skeleton` 元件） | 無 | 螢幕截圖 |
| 預設（已有資料） | 顯示目前 `store_settings` 的四個文字欄位與已上傳的 Logo／封面圖縮圖預覽 | 不適用 | 螢幕截圖 |
| 空狀態（首次使用，尚無資料列） | 文字欄位皆為空白（可直接編輯），Logo／封面圖顯示「尚未上傳」的上傳提示區塊 | 「尚未設定商店資訊」（表單上方提示文字，不阻擋編輯） | 螢幕截圖 |
| 編輯中 | 文字欄位可編輯；有未儲存變更時儲存按鈕從停用變為可點擊（比照既有「營業時間設定」慣例） | 無 | 螢幕截圖 |
| 儲存中 | 儲存按鈕顯示載入中並鎖定，欄位鎖定防止重複送出 | 無 | 螢幕截圖 |
| 儲存成功 | 顯示成功 Toast（沿用既有 `ToastProvider`） | 「已儲存」 | 螢幕截圖 |
| 驗證錯誤（店名空白） | 店名欄位顯示行內錯誤，儲存被前端擋下並聚焦到該欄位 | 「店名為必填」 | 螢幕截圖 |
| 圖片上傳中 | 對應的 Logo／封面圖上傳區塊顯示進度中狀態（覆蓋遮罩＋載入指示），該區塊的更換／移除按鈕暫時停用 | 無 | 螢幕截圖 |
| 圖片上傳錯誤 | 上傳區塊顯示行內錯誤，不影響已成功的其他欄位／圖片 | 「檔案格式需為 JPG／PNG／WebP」／「檔案大小需小於 5MB」 | 螢幕截圖 |
| 已設定的預覽態 | Logo／封面圖顯示縮圖預覽＋「更換」／「移除」按鈕 | 不適用 | 螢幕截圖 |
| 錯誤（查詢失敗） | 查詢 `store_settings` 失敗時顯示錯誤訊息＋重試 | 「無法載入商店設定，請重新整理再試一次」 | 螢幕截圖 |
| 權限不足 | 非 `is_admin()` 或未登入直接訪問 `/admin/store-settings` | 沿用既有 `/admin` 頁面的既有導回 `/login` 行為，不另立新邏輯 | 手動驗證 |
| 行動裝置版 | 非本階段重點，沿用既有後台「桌面/平板優先」決策 | 不適用 | 不適用 |

## 互動

| 動作 | 觸發條件 | 結果 | 失敗情境 |
|---|---|---|---|
| 編輯文字欄位 | 修改店名／地址／電話／簡介輸入框 | 即時前端驗證（店名非空白、電話基本格式、簡介長度上限），儲存按鈕啟用 | 不合法時該欄位顯示行內錯誤，送出被前端擋下並聚焦到第一個錯誤欄位 |
| 送出「儲存」（文字資訊） | 點擊儲存按鈕，且目前無前端驗證錯誤 | 寫入 `store_settings`，成功後顯示成功 Toast | 寫入失敗顯示通用錯誤 Toast，不外洩原始 Postgres 錯誤內容 |
| 選擇 Logo／封面圖檔案上傳 | 點擊上傳區塊選擇檔案，或拖曳檔案至上傳區塊 | 前端先驗證格式與大小，通過後立即上傳至 Supabase Storage 並更新 `store_settings` 對應 URL 欄位，成功後區塊切換為預覽態 | 格式／大小不符時顯示行內錯誤，不觸發上傳；上傳過程失敗顯示行內錯誤，維持原有圖片（若先前已有設定） |
| 更換既有 Logo／封面圖 | 在預覽態點擊「更換」，重新選擇檔案 | 同「選擇檔案上傳」流程，成功後以新圖取代（儲存路徑含雜湊／時間戳記，避免瀏覽器快取顯示舊圖） | 同上「格式／大小不符」「上傳失敗」情境 |
| 移除既有 Logo／封面圖 | 在預覽態點擊「移除」 | 清空對應 URL 欄位並寫入 `store_settings`，區塊切換回未上傳提示狀態 | 寫入失敗顯示通用錯誤 Toast，圖片預覽維持不變 |

## 設計系統對照

- 用到的既有 design token：`color.primary`（主按鈕、上傳區塊 hover 邊框）、`grey` 色階（次要
  文字、停用欄位背景、分隔線、上傳區塊預設邊框）、`danger`（驗證錯誤文字與邊框）、
  `radius.sm`（輸入框／按鈕／上傳區塊）、`radius.md`（卡片）、`elevation1` 陰影、`space` 4
  的倍數間距、type scale（`xs`/`sm`/`base`/`lg`）。
- 用到的既有元件：`Sidebar`（既有導覽，新增「商店設定」連結）、`TextField`（店名／地址／電話
  單行輸入）、`FormSection`（表單版面間距）、`Card`（區塊容器）、`Button`（儲存／更換／移除）、
  `ToastProvider`（成功/錯誤提示）、`Skeleton`（載入中）。
- 本畫面新做的元件：**圖片上傳（Image Upload Field）**——S4 inventory 目前沒有檔案上傳相關
  元件（本專案首次需要檔案上傳）。依既有 token 設計：預設態為虛線邊框（`grey.300`）＋置中
  提示文字與上傳圖示的可點擊／可拖放區塊（`radius.sm`）；已上傳態顯示縮圖（`radius.sm` 裁切）
  ＋右下角「更換」「移除」兩個小按鈕；上傳中態疊加半透明遮罩＋既有載入指示樣式；錯誤態邊框
  改為 `danger` 色並於下方顯示行內錯誤文字（比照既有欄位錯誤樣式）。實作階段（Phase 6）需
  依此設計做成 `components/ui/` 元件，完成後登記回 `design-system.md` 的 S4 inventory。

## 視覺驗收標準

- 文字在手機版與桌面版都不會被截斷（本階段桌面/平板優先，仍需基本自適應不破版）。
- 主要動作（儲存）清楚明確，且在有未儲存變更時才可點擊，避免誤觸空按鈕。
- 圖片上傳的三種狀態（未上傳／上傳中／已上傳）視覺區別明確，不會讓使用者誤以為上傳中就是失敗。
- 錯誤（驗證錯誤／上傳錯誤）與載入中狀態明確呈現，不與正常狀態混淆。
- 色彩、字體、間距、圓角、陰影一律取自 `design-system.md` 的 design token，沒有硬寫的一次性
  數值。
- 重複使用元件庫 inventory 裡的既有元件；新做的圖片上傳元件依既有 token 與風格製作，實作後
  需登記回 inventory。
