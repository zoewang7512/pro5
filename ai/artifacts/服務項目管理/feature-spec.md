# 功能規格書

## Metadata

- 功能：服務項目管理（對應 `tools/kanban/epics.json` 已登記的同名 Epic）
- 負責人：待指定
- 狀態：草稿（待人工核准）
- 風險等級：中（新增後台 CRUD 頁面與對應資料寫入路徑；`services` 資料表與 RLS policy 已於
  TASK-003 建立完成，本批次不需新增 migration，但需確認「下架」對既有預約流程／`create_appointment`
  RPC 的既有防護邏輯不受影響）
- 已與人工確認的範圍決策：
  - 「刪除或下架服務項目」本批次**只做下架**（`is_active = false`），不提供真正刪除資料列的功能。
  - 服務項目表單（新增／編輯）**不包含**緩衝時間（`buffer_minutes`），維持由「營業時間與可預約
    時段管理」Epic（TASK-022 起）管理，避免同一欄位在兩個 Epic 的介面都能修改造成混淆。

## 問題

- 目前完全沒有任何後台介面可以管理服務項目——`services` 資料表雖然已存在（TASK-003），且顧客
  前台已能瀏覽（`ServiceListSection.tsx`），但設計師無法自行新增、編輯或下架服務項目，只能請
  工程人員直接操作資料庫。
- 隨著店內服務調整（漲價、新增服務、停售某項服務），設計師需要能自主維護服務項目清單，不依賴
  工程人員介入。

## 使用者

- 設計師（後台唯一登入帳號，經 `is_admin()` 驗證）：直接使用者，新增、編輯、下架／重新上架
  服務項目。
- 顧客（前台，未登入）：間接受影響——預約流程第一步看到的服務項目清單，只包含目前上架
  （`is_active = true`）的項目；此故事已由既有顧客預約流程實作完成，本批次僅確認驗收標準
  無遺漏，不重新開發。

## 目標

- 讓設計師能在後台新增服務項目，填寫名稱、價格、時長、描述。
- 讓設計師能編輯既有服務項目的名稱、價格、時長、描述。
- 讓設計師能將服務項目下架（顧客端不再顯示、不可被選取預約），也能將已下架的項目重新上架。
- 後台服務項目列表要同時看得到上架與下架中的項目，並清楚區分兩種狀態。

## 非目標

- **真正刪除資料列**——沿用已確認的範圍決策，只做下架／重新上架；`appointments.service_id`
  外鍵未設定串聯刪除，真刪除有破壞歷史預約紀錄參照完整性的風險，不在本批次範圍。
- **緩衝時間（`buffer_minutes`）欄位**——維持由「營業時間與可預約時段管理」Epic 管理，本批次
  服務項目表單不顯示、不可編輯這個欄位。
- **服務項目分類／標籤**——`services` 表目前沒有分類欄位，需求也未提出，不在本批次範圍。
- **手動拖曳排序（`sort_order`）**——`services.sort_order` 欄位已存在且預設為 0，本批次新增／
  編輯表單不提供調整排序的介面，新項目一律沿用預設值；排序 UI 留待未來有明確需求時另立任務。
- **服務項目名稱唯一性檢查**——`services.name` 資料庫層沒有 unique 約束，本批次不新增，允許
  名稱重複（例如同名但不同時長的變體），不做前端／後端唯一性驗證。
- **圖片／封面**——服務項目本身不支援上傳圖片，與「商店基本資料設定」Epic 的 Logo／封面圖
  是不同性質的資料，不在本批次範圍。
- **顧客端瀏覽服務項目列表的介面改版**——已由既有顧客預約流程（`ServiceListSection.tsx`）
  實作，本批次不重新設計此畫面，僅在「驗收標準」確認既有行為符合本 Epic 的驗收語言。

## 功能需求

使用可測試的語言撰寫。

- WHEN 設計師在服務項目管理頁點「新增服務項目」並填寫名稱、價格、時長、描述後送出
  THE SYSTEM SHALL 驗證名稱非空白、價格為大於等於 0 的數字、時長為大於 0 的整數（分鐘），
  通過驗證後寫入 `services`（`is_active` 預設為 `true`）並顯示成功提示、更新列表；驗證失敗時
  阻擋送出並標示錯誤欄位。
- WHEN 設計師編輯既有服務項目的名稱、價格、時長或描述並儲存 THE SYSTEM SHALL 套用與新增相同
  的驗證規則，通過後更新該筆 `services` 資料列並顯示成功提示；不影響已使用該服務項目的既有
  `appointments` 資料。
- WHEN 設計師將上架中的服務項目點擊下架 THE SYSTEM SHALL 將該筆 `services.is_active` 設為
  `false`，後台列表即時反映狀態變更；顧客前台服務清單自此不再顯示該項目，且 `create_appointment`
  RPC 依既有邏輯（僅允許 `is_active = true` 的服務建立預約）拒絕針對該服務的新預約。
- WHEN 設計師將已下架的服務項目點擊重新上架 THE SYSTEM SHALL 將該筆 `services.is_active` 設為
  `true`，顧客前台服務清單自此重新顯示該項目、可被選取預約。
- WHEN 設計師檢視服務項目管理頁列表 THE SYSTEM SHALL 顯示所有服務項目（含上架與下架中），並以
  明確的視覺標示區分兩種狀態。
- WHEN 非管理員（含 anon 與已登入但非 `is_admin()` 的 authenticated 使用者）嘗試新增、編輯或
  變更服務項目上下架狀態 THE SYSTEM SHALL 拒絕該操作，沿用既有 `services` RLS policy
  （`admin full access to services`）。

## 資料與 API

- 輸入：沿用既有 `services` 資料表（TASK-003 建立，見 `supabase/migrations/0001_core_schema.sql`），
  不新增 migration：
  - `name text not null`（必填）
  - `description text`（選填）
  - `price numeric(10,2) not null check (price >= 0)`（必填）
  - `duration_minutes int not null check (duration_minutes > 0)`（必填）
  - `is_active boolean not null default true`（本 Epic 的下架／上架操作即寫入此欄位）
  - `sort_order int not null default 0`（本批次不提供編輯介面，新項目沿用預設值 0）
- 輸出：後台服務項目列表讀取全部服務項目（不受 `is_active` 過濾，需要 `is_admin()` 權限）；
  顧客前台維持既有 `is_active = true` 過濾查詢，不變更。
- 驗證：前端與資料庫（`check` constraint）皆驗證價格 ≥ 0、時長 > 0；名稱非空白為前端與後端
  共同驗證（資料庫目前僅 `not null`，允許純空白字串，後端邏輯需額外檢查避免存入純空白名稱，
  比照 `店名` 驗證模式）。
- 錯誤：資料庫錯誤時前端顯示通用友善訊息，不外洩原始錯誤內容，比照既有慣例
  （`lib/admin/` 既有錯誤處理模式）。

## 安全性與隱私

- 身分驗證：沿用既有 `is_admin()` + authenticated 邊界。
- 權限：沿用 `services` 既有 RLS policy——`admin full access to services`（僅 `is_admin()` 可
  新增／編輯／變更上下架狀態）、`public read active services`（anon／authenticated 僅可讀取
  `is_active = true` 的項目），本批次不需新增或修改 policy。
- 敏感資料：服務項目的名稱、價格、時長、描述皆為店家公開資訊，非個人隱私資料。
- 濫用情境：
  - 非管理員嘗試新增／編輯／下架服務項目，需在整合測試中驗證皆被拒絕（比照既有
    `test:business-hours`／`test:store-settings` 對 RLS 邊界的驗證模式）。
  - 描述欄位為使用者輸入的自由文字，前台渲染時需避免 XSS（沿用既有 React 預設跳脫，不使用
    `dangerouslySetInnerHTML`）。
  - 下架操作不得意外影響已存在的 `appointments` 資料（無串聯刪除、無串聯更新其他欄位）。

## 驗收標準

- 設計師可在後台「服務項目管理」頁新增服務項目（名稱、價格、時長必填，描述選填），新增後
  預設為上架狀態。
- 設計師可編輯既有服務項目的名稱、價格、時長、描述。
- 設計師可將上架中的服務項目下架、將已下架的服務項目重新上架，後台列表即時反映狀態。
- 下架的服務項目不會出現在顧客前台服務清單，也無法透過 `create_appointment` RPC 被用來
  建立新預約；已存在的相關預約紀錄不受影響。
- 非管理員（anon／非管理員 authenticated）無法新增、編輯服務項目或變更上下架狀態。
- 既有測試（`test:rls`／`test:booking`／`test:admin-booking`／`test:business-hours`／
  `test:store-settings`）重跑無回歸；顧客前台既有服務清單行為（載入中／載入失敗／空狀態）
  不受影響。

## 驗證計畫

- 單元測試：名稱／價格／時長欄位的前端驗證邏輯（純函式）。
- 整合測試：對真實 Supabase 專案驗證 `services` 的 RLS 邊界（anon／非管理員 authenticated
  只能讀取上架項目、寫入被拒；`is_admin()` 可新增／編輯／變更上下架狀態）；下架後
  `get_available_slots`／`create_appointment` 對該服務的行為（不可用於新預約）；驗證後還原
  測試資料，避免污染正式服務清單。
- E2E：Browser 工具桌面尺寸走查（後台新增服務項目、編輯既有項目、下架後切到前台確認清單
  不再顯示、重新上架後前台恢復顯示）。
- 視覺：服務項目管理頁的畫面狀態表，涵蓋預設／新增表單／編輯表單／驗證錯誤／空狀態，比照
  `design-craft` 檢查表。
- 手動：確認下架操作後，若該服務項目已有既有預約，該筆預約詳情仍可在「預約管理後台」正常
  查看，不因服務下架而顯示錯誤或缺漏資料。
