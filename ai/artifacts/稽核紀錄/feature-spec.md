# 功能規格書

## Metadata

- 功能：稽核紀錄（簡版：後台操作日誌）
- 負責人：待指定
- 狀態：人工已核准（使用者，2026-10-24；範圍由使用者於 2026-10-23 選定「簡版 A」）
- 風險等級：中。新增一張表與一組薄封裝，接到既有後台寫入函式；**不碰顧客預約的寫入路徑**，記錄失敗不影響原操作。
- 與先前完整版的關係：原本規劃的防竄改完整版（資料庫 trigger、測試標記＋密鑰、9 張任務卡）已擱置，文件保留在 `完整版備案/`。使用者的初衷是「簡單記錄店長有過什麼操作」，簡版即為此目的。
- 已與人工確認的範圍決策：
  - 記錄範圍：預約（完成、取消、改期）＋影響可預約性的設定（預約規則、營業時間、公休日、服務、設計師、設計師服務、請假日）。
  - 不存顧客個資（姓名、電話、email）。
  - 實作方式：在後台寫入函式成功後多寫一筆紀錄（簡版 A）。

## 問題

後台的寫入都由瀏覽器直接對 Supabase 進行，資料表只留 `updated_at`，**事後無法回答「店長在什麼時候做了什麼操作」**。預約被取消或改期、設定被改動（尤其是會讓前台突然沒有時段的設定）時，沒有任何線索可以追查。

## 使用者

- 店長（後台唯一登入帳號，經 `is_admin()` 驗證）：查看自己的操作紀錄。

## 目標

- 店長在後台做的關鍵操作**成功之後**自動記一筆：誰、什麼時候、做了什麼、改了什麼（前後值）。
- 後台有一個列表可以查看，最新的在最上面，可依類別（全部／預約／設定）篩選。
- 記錄失敗**不影響**原本的操作。
- 紀錄寫入後不能被修改或刪除（一般登入帳號層級），紀錄裡的「操作者」由資料庫決定、不能由前端指定。
- 紀錄不含顧客個資。

## 非目標

- **防竄改**：這是操作日誌，不是防竄改稽核。被盜用的店長 session 仍可新增偽造的紀錄（但改不了、刪不掉既有紀錄）；資料庫 owner／Dashboard／service key 仍可改動資料表。
- **繞過後台的操作**：直接呼叫 Supabase API、使用 service key、在 SQL Editor 的操作，不會被記錄。
- **顧客行為**：顧客建立預約不記錄（不是店長操作）。
- **寄信、cron 提醒、登入／登出／MFA／改密碼事件**：不記（登入事件可到 Supabase Dashboard 的 Auth logs 查）。
- **商店基本資料、Logo／封面圖、設計師簡介／專長／IG／頭像／作品集／排序、帳號個人資料**：不記；日後要加，只需在對應函式多一行呼叫。
- **歷史資料回補**：從上線當下才開始記。
- **編輯、刪除、匯出、保留期限自動清理**：列表唯讀；永久保留（預估每年遠低於一萬筆）。
- **日期區間與預約編號篩選、預約詳情內嵌歷史、總筆數、即時通知／警示**：本次不做，日後可加。
- **行動裝置版面**：沿用既有後台非目標，桌面為主。

## 功能需求

### 1. 資料表與寫入

- THE SYSTEM SHALL 提供 `audit_log` 資料表，欄位：流水號、發生時間（資料庫端預設，前端不可指定）、操作者 id（資料庫端預設為目前登入者，前端不可指定）、事件代碼、對象類型、對象 id、摘要快照、欄位前後差異。
- THE SYSTEM SHALL 只允許通過 `is_admin()` 的登入者新增與讀取；anon 無任何權限；任何角色都不能 update／delete（`service_role` 只保留 select 與 delete，供整合測試清理）。
- THE SYSTEM SHALL 提供 `recordAdminAction`：在原操作成功之後呼叫；任何失敗（網路、權限、資料庫）只在 console 留警告，**不 throw、不改變原操作的回傳結果**。
- THE SYSTEM SHALL 在 `recordAdminAction` 內截斷文字值（60 字）並限制摘要大小，使紀錄寫入不因內容過長而失敗。

### 2. 事件

只在原操作**成功且有實際變動**時記錄。寫入前先讀一次舊值（讀不到就只記新值，不阻擋操作）。

| `updateBusinessHours` | `business_hours.updated`（一次儲存一筆） | 有變動的星期 | 各星期的營業起訖時間與是否公休（前→後） |
| `addClosedDate`／`removeClosedDate` | `closed_date.added`／`closed_date.removed` | 日期 | — |

### 3. 列表（後台 `/admin/audit-log`）

- WHEN 店長開啟頁面，THE SYSTEM SHALL 以流水號倒序載入第一頁（每頁 50 筆），可「載入更多」；僅店長可見。
- THE SYSTEM SHALL 對每列顯示：發生時間（Asia/Taipei）、事件（中文）、對象摘要、前後差異（例如「最短提前預約時間：2 小時 → 720 小時」）；一律以純文字渲染。
- THE SYSTEM SHALL 提供類別篩選（全部／預約／設定），篩選在資料庫端執行。
- WHEN 查詢失敗，THE SYSTEM SHALL 顯示錯誤狀態與重試，不顯示部分資料；WHEN 沒有結果，顯示空狀態並區分「尚無任何紀錄」與「此類別沒有紀錄」。

## 資料與 API

- 輸入：後台寫入函式成功後的事件資料；列表端為類別與游標。
- 輸出：`audit_log` 列；中文事件名稱與差異文字由前端依事件代碼組成，不存資料庫。
- 驗證：事件代碼為固定格式（`^[a-z_]+\.[a-z_]+$`）；摘要與差異為 JSON 物件且有大小上限；寫入前於前端函式截斷文字。
- 錯誤：寫入失敗＝只警告；讀取失敗＝錯誤狀態，訊息為泛用文字，不洩漏資料庫內容。
- 新增 migration `0019`（up／down 成對），建表時依 `decisions.md` TASK-065 在同檔寫出最小權限 GRANT。

## 安全性與隱私

- 身分驗證：列表走既有 `app/admin/layout.tsx` 三層檢查；資料層走 `is_admin()`（已啟用 MFA 的帳號需 aal2，見 0016）。
- 權限：anon 零權限；authenticated 只有 select 與欄位層級 insert（事件代碼、對象、摘要、差異），**不含**操作者與時間欄位，這兩欄由資料庫預設決定；沒有 update／delete 授權與 policy。
- 敏感資料：不存顧客個資；寫入的欄位由程式碼白名單決定，並以單元測試保證各事件的摘要不含顧客欄位。
- 保證邊界（如實記錄）：能防止登入帳號**修改或刪除**既有紀錄與**偽造操作者**；不能防止被盜用的店長 session **新增**偽造紀錄、繞過後台的操作、資料庫 owner／service key。這是操作日誌，不是防竄改稽核。

## 假設

- 後台只有一位店長帳號，列表不顯示操作者（欄位仍保留，日後有第二位管理員時可顯示）。
- 永久保留；時區顯示固定 Asia/Taipei。
- 整合測試若呼叫這些函式，會在日誌留下測試紀錄：帶 `__TEST__` 名稱的可用清掃腳本清除；不帶名稱的（例如預約規則、營業時間還原）可能留下少量雜訊，屬已接受。

## 風險

1. **日誌可能漏記**：記錄失敗只警告（刻意不影響原操作）；使用者在寫入前關閉分頁也會漏記。
2. **繞過後台就記不到**：直接打 API、service key、SQL Editor 都不會留紀錄。
3. **被盜用的店長 session 可新增偽造紀錄**（但改不了、刪不掉既有紀錄）。
4. **既有單元測試可能需調整**：後台寫入函式多了一次 `audit_log` 寫入與舊值讀取，依賴呼叫次數或逐次回傳的 mock 可能受影響。
5. **每次操作多 1～2 個查詢**（舊值讀取＋寫入）；操作頻率低，可忽略。
6. **測試雜訊**：見假設。
7. **只記錄、不通知**：帳號被盜用時只留證據，不會主動告警。

## 驗收標準

- 事件表中的 16 個來源函式在「成功且有實際變動」時各留下預期事件；失敗或無變動時不留；紀錄失敗時原操作結果不變。
- 紀錄表權限：anon 的任何操作被拒；非店長登入者 select 得到空結果、insert 被拒；店長可 insert、select，不能 update、delete；店長 insert 時無法指定操作者與時間（欄位層級拒絕）。
- 各事件摘要與差異的鍵集合嚴格屬於事件白名單，不含顧客個資。
- 後台 `/admin/audit-log` 可看到上述紀錄，類別篩選與載入更多運作，載入中／空／錯誤狀態皆可重現。

## 驗證計畫

- 單元測試：`recordAdminAction`（失敗不 throw、截斷、大小限制）；每個來源函式「成功才記、失敗不記、記錄失敗不影響結果、無變動不記」；事件白名單與顧客欄位不外洩；事件代碼→中文、差異→白話（時區不依賴環境）；`listAuditLog` 查詢組成；列表元件各狀態。
- 整合測試（新增 `npm run test:audit-log`）：權限矩陣（anon／非店長登入者／店長 × select／insert／update／delete；欄位層級 insert）；店長實際呼叫來源函式（用 `__TEST__` 資料）後可在 `audit_log` 讀到對應紀錄；測試資料以 `scripts/sweep-audit-test-rows.mjs` 清掃。
- E2E：無（專案目前沒有 E2E 套件）。
- 視覺：列表頁桌面版截圖，對照 `ai/checklists/design-review-checklist.md`；淺色／深色各一。
- 手動：店長在後台做一輪「取消、改期、改最短提前時間、停用設計師」，再到稽核紀錄頁逐筆比對。
