# 功能規格書

## Metadata

- 功能：Demo 體驗帳戶（新 Epic，核准後登記到 `tools/kanban/epics.json`）
- 負責人：待指定
- 狀態：人工已核准（使用者，2026-10-30，以回覆三項阻擋性問題並要求進入 UI 確認為準）
- 風險等級：高。這個 Epic 同時做三件有風險的事：
  - 對正式 Supabase 專案的 `auth` schema 加觸發器（鎖住 Demo 帳戶的密碼、Email、MFA 異動）。
  - 一支用 service_role 執行、會**整張表覆寫**正式庫資料與 Storage 圖片的還原機制，而且會排程無人值守地執行。
  - 公開一個「一鍵就能取得後台管理員權限（`is_admin()` 為真）session」的入口，等同公開後台。
  - 需要架構、安全性、測試三方審查。
- 已與人工確認的範圍決策（2026-10-29）：
  - **同一個 Supabase 專案與正式站**，不另開獨立環境。理由：本專案是面試作品、沒有真實店家（見 `TASK-080` 延後決定），隔離環境要多維護 20 支 migration、第二個 Vercel 專案與 Database Webhook，成本大於效益。
  - **Demo 帳戶後台功能全開**，唯獨禁止三件事：改密碼、改 Email、啟用 MFA。不採唯讀，因為本專案的賣點都是寫入流程（改期、時段衝突擋下、設計師請假、營業時間連動可預約時段）。
  - **還原範圍涵蓋服務、設計師、預約、營業時間、店家設定與 Storage 圖片**；`designer001` 與使用者手動調過的資料也會被還原成 seed 快照（使用者已明確接受）。
  - **作品集與頭像圖片由使用者人工產生後放進 seed**。**關卡：做 seed 之前，必須先向使用者確認「作品集已補完」**，得到肯定回答才可開始 seed 與圖片匯入。
  - 鎖採三層：前端隱藏／停用、資料庫觸發器（待小實驗驗證可行）、還原腳本重設。
  - **登入頁入口改為「一鍵直接進入」（使用者，2026-10-30，mockup 決策）**：面試官按下「進入體驗帳號」就直接登入後台，不需要輸入或看到任何帳密，進入後立即彈出說明視窗。這**推翻**本文件早先「只填入欄位、不自動送出」與「不做伺服器端一鍵登入」的決定；由伺服器端代為登入，Demo 密碼只存在伺服器環境變數，不顯示在畫面或 README。
  - mockup 選定：登入頁 A（一鍵進入版）、帳號設定頁鎖定狀態 A（保留三張卡片並停用）、後台提示 A（頂端橫幅，可關閉）。

## 已確認的阻擋性決定（使用者，2026-10-30）

1. **還原只動業務資料（設計師資料、頭像、服務等），不動 `designer001` 的登入密碼、Email 與 MFA。** 排程無人值守，若覆寫憑證，一旦 seed 與實際密碼不同，使用者會被鎖在後台外面。
2. **Demo 預約寄信：開啟。** 推翻 `TASK-080` 原寫的「Demo 環境關閉寄信」（實作時須同步更新該卡註記與 `decisions.md`）。緩解措施沿用：同一 Email 最多 3 筆待服務預約、Resend 每日上限，被濫用時可用環境變數關閉。
3. **加上「體驗帳號提示橫幅」（故事 S6）。** 面試官需要知道資料會被還原、三項被鎖，否則會誤以為壞掉。

## 問題

- 面試官想體驗後台，但沒有帳號可登入。使用者花最多時間做的後台機制（預約管理、設計師管理、營業時間、稽核紀錄、報表）完全看不到，展示價值大打折扣。
- 正式站就是展示站，但後台只有一個設計師管理員帳號（`designer001`），不能公開，也不能讓外人隨意改動。
- 若直接公開管理員帳密，面試官可以改密碼把其他人鎖在外面、改 Email、啟用 MFA 讓帳號無法使用，或把資料改得無法展示。

## 使用者

- 面試官（直接使用者）：未登入的訪客，想在幾分鐘內操作後台主要功能，也會以顧客身分走一次前台預約流程。
- 專案作者（使用者本人）：維護 Demo 資料、執行還原、面試時用自己的帳號展示。

## 目標

- 面試官在登入頁按一下就進入後台（不需輸入任何帳密），並看到說明視窗，能操作後台所有業務功能。
- Demo 帳戶無法改密碼、改 Email、啟用或停用 MFA，不論是透過畫面或直接呼叫 Supabase Auth。
- 展示資料完整豐富（服務、設計師與作品集、預約歷史與未來預約、公休日、店家設定），讓儀表板與報表有內容可看。
- 資料會自動且完整地還原成 seed 快照，面試官改亂也不會長久影響下一位。
- 還原過程不會讓使用者自己的登入失效，也不會寄出非預期的信。

## 非目標

- **另開獨立 Supabase 專案或獨立部署**：已決定不做。
- **唯讀 Demo 角色**：已決定不做。
- **公開顯示體驗帳號的帳密**：不做。一鍵進入由伺服器端代為登入，帳密不出現在畫面、README 或前端程式碼。
- **一般管理員也走一鍵進入**：不做。一鍵進入只會登入 Demo 帳戶，不能指定其他帳號。
- **多個 Demo 帳戶、每位面試官各自獨立沙盒**：不做。所有面試官共用同一組帳號與同一份資料，會互相看到對方的修改，這是已知取捨。
- **產生 AI 圖片**：圖片由使用者人工產生，本 Epic 只負責匯入。
- **Demo 帳戶的使用量統計、訪客追蹤**：不做。
- **為 Demo 做 MFA 示範**：Demo 帳戶永遠不啟用 MFA。

## 功能需求

### 帳戶與登入

- WHEN 執行 Demo 帳戶建立腳本 THE SYSTEM SHALL 以 service_role 建立帳戶、設定 `app_metadata.is_demo = true`、登記 `admins`，且重跑不重複建立。
- WHEN 使用者按下登入頁「進入體驗帳號」 THE SYSTEM SHALL 由伺服器端以 Demo 帳戶登入、建立 session 並導向後台，使用者不需輸入或看到任何帳密。
- WHEN 一鍵進入成功進入後台 THE SYSTEM SHALL 立即顯示說明視窗一次（可以體驗：預約週曆、改期、取消、標記完成；設計師、作品集、請假與服務設定；營業時間、公休日、儀表板與報表。不開放：修改密碼、登入 Email；啟用／停用雙重驗證（MFA）），按「開始體驗」或 Esc 關閉。
- WHEN 一鍵進入失敗（網路、Demo 帳戶不存在或環境設定缺漏） THE SYSTEM SHALL 在登入頁顯示「目前無法進入體驗帳號，請稍後再試。」，不洩漏原因細節，且一般登入仍可使用。
- WHEN 同一來源短時間重複觸發一鍵進入 THE SYSTEM SHALL 限流並拒絕多餘請求。
- WHEN 一鍵進入的端點收到任何參數 THE SYSTEM SHALL 忽略，只登入固定的 Demo 帳戶，不得指定其他帳號。
- WHEN 環境變數未設定 Demo 帳戶 THE SYSTEM SHALL 不渲染體驗入口，登入頁與現況一致。
- WHEN 使用者用 Email 與密碼表單登入 THE SYSTEM SHALL 維持既有登入流程與限流，不受影響。
- THE SYSTEM SHALL NOT 讓 Demo 帳戶具備任何 verified MFA factor。

### 鎖帳號安全

- WHEN Demo 帳戶嘗試修改密碼 THE SYSTEM SHALL 拒絕，不論是透過畫面或直接呼叫 `supabase.auth.updateUser({ password })`。
- WHEN Demo 帳戶嘗試修改 Email THE SYSTEM SHALL 拒絕，同上。
- WHEN Demo 帳戶嘗試註冊或移除 MFA factor THE SYSTEM SHALL 拒絕。
- WHEN 在登入頁對 Demo 帳戶 Email 觸發忘記密碼 THE SYSTEM SHALL 不寄出重設信，並顯示與一般「已寄出」相同或明確的提示（細節於架構階段決定）。
- WHEN 非 Demo 帳戶執行上述任一動作 THE SYSTEM SHALL 維持現有行為，不受影響。

### 還原

- WHEN 觸發還原 THE SYSTEM SHALL 將下列表格整張還原成 seed 快照：`services`、`designers`、`designer_services`、`designer_leaves`、`designer_portfolio_images`、`business_hours`、`closed_dates`、`store_settings`、`booking_policy`、`appointments`、`customers`，以及 Storage 的三個 bucket（店家素材、管理員頭像、設計師素材）。`audit_log` 與 `admins` 是否納入由架構階段決定（見資料與 API）。
- WHEN 還原中途失敗 THE SYSTEM SHALL 保留還原前的資料，不留下半套狀態。
- WHEN 還原寫入 `appointments` THE SYSTEM SHALL 確保不觸發任何寄信（seed 預約 `customer_email` 一律為 null）。
- WHEN 還原結束 THE SYSTEM SHALL 重設 Demo 帳戶的密碼、Email 與 MFA 狀態，且 SHALL NOT 更動 `designer001` 的任何 auth 憑證。
- WHEN 排程端點收到沒有正確密鑰的請求 THE SYSTEM SHALL 拒絕且不執行任何還原。
- WHEN 還原執行 THE SYSTEM SHALL 在伺服器端記錄開始、結束、成功或失敗與涉及筆數，不記錄任何密碼或金鑰。

### Seed 資料

- WHEN 執行 seed THE SYSTEM SHALL 產生過去與未來都有的預約，使儀表板與報表有內容；日期以執行當下為基準相對計算，不寫死絕對日期。
- THE SYSTEM SHALL 只在使用者確認作品集補完後才匯入圖片與作品集資料。

## 資料與 API

- 輸入：
  - 環境變數：Demo 帳戶 Email 與密碼、還原排程密鑰（新增，需補 `.env.example`；Vercel 上同步設定）。
  - seed 檔：資料快照與圖片素材，存在專案內（位置由架構階段決定）。
- 輸出：Demo 帳戶、還原後的資料與圖片；伺服器端記錄。
- 驗證：Demo 識別一律用 `app_metadata.is_demo`（使用者無法自行修改，只有 service_role 能設定），不得用 Email 字串比對。
- 錯誤：還原失敗回報原因與已完成步驟；被鎖動作回傳可辨識的錯誤，前端顯示「體驗帳號不開放」。
- **架構階段要決定的事**：
  - 還原是否做成單一 SECURITY DEFINER RPC（僅 service_role 可執行）在同一個交易內完成，才能達成原子性；Supabase JS client 本身沒有跨表交易。
  - `audit_log` 是否納入還原。稽核紀錄可能被刻意設計成不可改，需先讀 `0019_audit_log.sql` 確認，並避免 Demo 操作留下大量紀錄汙染報表。
  - `admins` 表不得被還原動到 `designer001` 的登記。
  - `auth.users` 與 `auth.mfa_factors` 觸發器的可行性與副作用（見驗證計畫的小實驗）。
  - 還原中途面試官正在操作時的行為（建議排在低流量時段，並承認短暫不一致）。
  - 排程頻率與 Vercel 方案限制：現有 `vercel.json` 已有一個每日 cron，需確認方案允許再加一個。
  - 一鍵進入端點：用 Route Handler 還是 Server Action、如何與 `@supabase/ssr` 的 cookie 寫入整合、限流方式（serverless 環境不能靠記憶體計數）、是否擋非同源請求（CSRF／跨站觸發）、成功後導向與說明視窗「每次一鍵進入顯示一次」的旗標如何傳遞（例如進入時清除 sessionStorage 旗標）。

## 安全性與隱私

- 身分驗證：一鍵進入是**新增的公開端點**，在伺服器端以 Demo 帳戶呼叫 Supabase 密碼登入並設定 session cookie，等同「誰都能取得 Demo 管理員 session」。因此安全性不依賴密碼保密，而依賴「能做的事被限制」（三項帳號安全鎖、`is_admin()` 寫入面盤點）與「資料會還原」。Demo 密碼應為長隨機值，只存在伺服器環境變數，不顯示、不進前端 bundle、不寫入 log；端點只能登入固定的 Demo 帳戶，不得指定帳號。
- 權限：Demo 帳戶透過 `is_admin()` 取得管理員寫入權限。**必須逐表盤點**：
  - 不能新增或刪除 `admins` 登記、不能提權。
  - 不能讀到或改動 `designer001` 的 auth 資料。
  - 公開 bucket 上傳仍受 5MB、副檔名與作品集張數上限約束，避免被塞滿空間。
- 敏感資料：Demo 密碼與還原密鑰只放環境變數與 Vercel，不進版控、不寫入 log。還原腳本使用 service_role，須沿用 `import "server-only"` 與現有 service-role client 的限制。
- 濫用情境：
  - 面試官改亂資料：由還原處理。
  - 機器人或腳本反覆打一鍵進入端點：端點限流；Supabase Auth 本身另有登入限流；Demo 帳戶 session 可被大量建立，須確認不會耗盡 Auth 額度（架構階段評估）。
  - 面試官用顧客身分大量預約並借本站寄信：沿用「同 Email 最多 3 筆」與 Resend 上限；可用環境變數關閉寄信。
  - 面試官嘗試繞過前端直接呼叫 Auth API 改密碼：由資料庫觸發器擋下；若觸發器不可行，退而求其次靠還原腳本重設，並承認這段時間可能影響下一位面試官。
  - 排程端點被外部呼叫：密鑰保護，並確保即使被觸發也只是還原成 seed，不外洩資料。
  - 整合測試誤對正式庫跑完整還原：測試只能用 dry-run 或會回滾的交易，不得真的清空正式資料。
- 既有教訓必須遵守：測試預約一律 `customer_email = null`；測試腳本結尾不得對店長帳號做全域 `signOut()`，用 `scope: "local"`；`vi.mock` 擋不住資料庫自己的 Database Webhook 觸發器。

## 驗收標準

- Demo 帳戶存在、為管理員、有 `is_demo` 標記、沒有 MFA；重跑建立腳本不產生重複。
- 在登入頁按「進入體驗帳號」後，不輸入任何帳密就進入後台，並看到說明視窗；能操作後台的服務、設計師、預約、營業時間、公休日、店家設定、預約規則與報表。
- 一鍵進入失敗時顯示指定文案，且一般登入不受影響；短時間重複觸發會被限流；前端程式碼、回應與 log 中找不到 Demo 密碼。
- Demo 登入時，密碼、Email、MFA 三項在畫面上停用；用 console 直接呼叫對應的 Supabase Auth API 會失敗（或在觸發器不可行時，有文件化的替代緩解）。
- 非 Demo 管理員的改密碼、改 Email、MFA 流程不受影響（既有 `test:account`、`test:mfa-rls` 仍通過）。
- 還原後，上述表格與 bucket 內容等同 seed 快照；Demo 憑證被重設；`designer001` 的登入憑證沒有被改動；沒有任何信被寄出。
- 還原失敗時，還原前的資料完整保留。
- 排程端點沒有正確密鑰時回 401 或 403，且資料不變。
- seed 的預約橫跨過去與未來，儀表板與報表有非零資料。
- 作品集補完確認這個關卡有被執行並留下紀錄（使用者確認訊息或驗證報告）。
- README、`.env.example`、`decisions.md` 已同步；`TASK-080` 的「Demo 環境關閉寄信」註記依你的決定更新。

## 驗證計畫

- 單元測試：Demo 識別函式（只認 `app_metadata.is_demo`）；前端三項停用邏輯；登入頁填入按鈕只填不送；排程端點的密鑰檢查。
- 整合測試（對真實 Supabase，必須遵守既有教訓）：
  - 用**拋棄式帳號**（非 Demo 與 Demo 各一）驗證觸發器：Demo 改密碼、Email、MFA 失敗，非 Demo 成功；測完清除。
  - 還原只用 dry-run 或會回滾的交易驗證原子性與範圍，**不對正式庫跑真實完整還原**；真實還原僅在使用者核准的手動驗收時執行一次。
  - 驗證還原後 `designer001` 的 auth 資料不變（比對雜湊或時間戳，而不是只看登入成功）。
- E2E：從登入頁按「進入體驗帳號」開始，確認說明視窗與橫幅出現，走一次後台主要操作與前台預約流程。
- 視覺：登入頁區塊、帳號設定頁停用狀態、橫幅在亮色與暗色、手機寬度，附螢幕截圖。
- 手動（需使用者人工驗收）：
  - 確認作品集補完後才跑 seed。
  - 在正式站實際用 Demo 帳號操作、故意改亂後觸發還原，確認恢復。
  - 確認你自己的 `designer001` 仍可正常登入。
  - 檢查沒有收到非預期的信。
- 動工前小實驗：在拋棄式帳號上確認 `auth.users` 與 `auth.mfa_factors` 加觸發器可行，且不會擋到登入時 Auth 自己的內部更新（例如 `last_sign_in_at`）。這個結果決定第二層鎖要不要做。
