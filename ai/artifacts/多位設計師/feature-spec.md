# 功能規格書

## Metadata

- 功能：多位設計師（新 Epic，核准後登記到 `tools/kanban/epics.json`）
- 負責人：待指定
- 狀態：人工已核准（使用者，2026-10-21）
- 風險等級：高。這個 Epic 會推翻「全店只有一位設計師」的既有前提：
  - `appointments_no_overlap` exclusion constraint 要從「全店不可重疊」改成「同一位設計師
    不可重疊」，見 `supabase/migrations/0002_booking_flow.sql` 的說明：「不以 service_id
    分割——只有一位設計師」。
  - 要修改 `get_available_slots`／`create_appointment` 這兩支顧客端唯一的預約讀寫路徑，
    並新增「不指定設計師」的自動指派邏輯，這部分有併發風險。
  - 新增一個 Storage bucket 放設計師頭像與作品集，還有一個顧客可見的外部連結（IG）。
  - 需要架構、安全性、測試三方審查。
- 已與人工確認的範圍決策（2026-10-21）：
  - **由店長一個帳號管理所有設計師**。設計師本身不登入後台，認證模型（`admins`／
    `is_admin()`）維持不變。
  - **營業時間共用全店設定**（`business_hours`／`closed_dates`），設計師只能另外設定
    **整天請假**，不能設定各自的營業時間，也不能請半天或指定時段的假。
  - **價格全店統一**，`services.price` 不因設計師而不同。店長可以替每位設計師開關要提供
    哪些服務。
  - **後台可以上傳設計師頭像與作品集圖片**（存在 Supabase Storage）。前台用仿 IG 個人
    頁面的版型呈現。目前圖片素材先用 AI 產生的圖，**不串接 Meta／Instagram API**。
  - **顧客流程是先選服務、再選設計師**，可以選「不指定設計師」。選「不指定」時，系統在
    預約**送出時自動指派**一位有空的設計師。
  - **這次不做「改派設計師」**。預約建立後設計師就固定，後台改期只能換時間、不能換人。
  - 「顧客自助查詢／取消／改期」與「顧客資料管理」兩個 Epic 延後，不在本 Epic 範圍。

## 問題

- 目前系統假設全店只有一位設計師：可預約時段是以「全店」為單位計算，只要任何一筆預約
  佔用了某個時段，該時段就對所有顧客都不可預約。店裡有多位設計師時，這會讓同一個時段
  實際上只能接一位客人，產能被嚴重低估。
- 顧客沒辦法選擇或認識設計師。他們看不到各設計師擅長什麼、看不到過去的作品，只能憑
  運氣被安排。
- 店長沒辦法管理各設計師的基本資料、提供哪些服務、什麼時候請假，也沒辦法在後台週曆上
  分辨某筆預約是哪位設計師負責。

## 使用者

- 店長（後台唯一登入帳號，經 `is_admin()` 驗證）：直接使用者。新增、編輯、停用設計師，
  設定每位設計師提供的服務、作品集與請假日，在週曆上依設計師檢視預約。
- 顧客（前台，未登入，以行動裝置為主）：直接使用者。選完服務後選擇設計師（或不指定），
  可以查看設計師的專長、IG 連結與作品集。
- 設計師本人：不登入系統，只是被管理的資料對象。

## 目標

- 可預約時段改成「依設計師」計算。同一個時段，不同設計師可以各自接一位客人。
- 店長可以在後台完整管理設計師：基本資料、頭像、專長、IG 帳號、提供的服務、作品集、
  請假日。
- 顧客選完服務後，可以挑選有提供該服務的設計師，或選「不指定設計師」，並且可以查看
  設計師的詳細資訊。
- 選「不指定設計師」時，系統會自動、穩定、而且不會撞期地指派一位設計師。
- 後台週曆／列表、預約詳情與四種通知信都會顯示這筆預約的設計師。
- 既有預約與既有流程可以無痛升級：現有的預約都會歸給一位「預設設計師」，升級後顧客端
  行為與現在一致（只有一位設計師時，等同現行邏輯）。

## 非目標

- **設計師登入後台／各自的帳號與權限**：已確認由店長一個帳號統一管理。
- **設計師各自的每週營業時間／班表**：全店共用 `business_hours`。只有整天請假可以各自
  設定。
- **半天或指定時段的請假**：只支援整天。
- **依設計師設定不同價格或不同服務時長**：`services.price`／`duration_minutes`／
  `buffer_minutes` 全店統一。
- **改派設計師**：後台改期維持同一位設計師。要換設計師只能先取消，再請顧客重新預約。
  連帶的影響是，設計師請假時，當天已經有的預約不會自動改派，也不會自動通知顧客（比照
  既有公休日的處理方式），只會顯示警告，由店長手動處理。
- **串接 Instagram／Meta API**：IG 只存帳號名稱並組成外部連結。作品集是本系統自己上傳的
  圖片，只是畫面仿 IG。
- **產生 AI 圖片**：作品集與頭像的圖片素材由人工用 AI 工具產生後，透過後台上傳（或之後
  由 Demo 帳戶的 seed 匯入）。本 Epic 不負責產生圖片，mockup 階段用占位圖。
- **作品集拖曳排序、圖片說明文字、按讚／留言等 IG 互動**：作品依上傳時間排序，可以新增、
  刪除，但不能調整順序。
- **硬刪除設計師**：只能停用，以保留歷史預約的關聯。
- **顧客自助查詢／取消／改期、顧客資料管理、儀表板中依設計師統計**：屬於其他 Epic。
  儀表板 Epic 之後可以直接使用本 Epic 建立的 `designer_id`。
- **「不指定」自動指派策略讓店長自行設定**：策略固定（見功能需求），不提供設定介面。

## 功能需求

### 設計師資料管理（後台）

- WHEN 店長新增或編輯設計師並送出 THE SYSTEM SHALL 驗證：名稱必填，1～30 字（去除前後
  空白後）；簡介選填，200 字以內；專長標籤 0～5 個，每個 1～12 字、不可重複；IG 帳號選填，
  只能是 Instagram 帳號名稱格式（英數、`.`、`_`，1～30 字，可以省略開頭的 `@`）。通過後
  寫入並顯示成功提示，失敗則在對應欄位顯示錯誤。
- WHEN 店長上傳設計師頭像 THE SYSTEM SHALL 只接受 jpg/png/webp、5MB 以內的圖片，存到
  設計師專用的 Storage bucket；沒有頭像時，前後台都顯示名字首字的預設頭像。
- WHEN 店長停用設計師 THE SYSTEM SHALL 二次確認，並顯示該設計師「未來的有效預約」筆數
  警告（不阻擋，也不自動取消）；停用後前台設計師列表、`get_available_slots`、
  `create_appointment` 都不再把他列入候選。
- WHEN 店長重新啟用設計師 THE SYSTEM SHALL 恢復他在前台的顯示與可預約狀態，原本的服務
  開關、作品集、請假日都保留。
- WHEN 店長停用最後一位啟用中的設計師 THE SYSTEM SHALL 在確認對話框明確警告「前台將沒有
  任何可預約的設計師」，但仍允許操作（比照既有服務下架不阻擋的精神）。
- THE SYSTEM SHALL 讓店長調整設計師在前台的顯示順序（`sort_order`）。這個順序也是自動
  指派時「同分」的決勝依據。

### 設計師提供的服務

- WHEN 店長替某位設計師開啟或關閉某項服務 THE SYSTEM SHALL 立即儲存，且前台設計師列表與
  時段計算都依照最新設定。
- WHEN 關閉某項服務時，該設計師還有這項服務的未來有效預約 THE SYSTEM SHALL 保留這些既有
  預約不動（不自動取消），只影響之後的新預約。
- WHEN 店長新增一項服務 THE SYSTEM SHALL 預設**不對任何設計師開啟**，並在新增成功提示中
  提醒店長去設計師頁開啟（避免新服務被意外開給所有人）。**例外**：升級 migration 會把
  既有的全部服務都對「預設設計師」開啟，維持升級前的行為不變。
- WHEN 顧客端讀取服務列表 THE SYSTEM SHALL 只列出「上架中，而且至少有一位啟用中的設計師
  有開啟」的服務。

### 作品集

- WHEN 店長上傳作品圖片 THE SYSTEM SHALL 只接受 jpg/png/webp、單張 5MB 以內的圖片，每位
  設計師最多 12 張，超過上限時拒絕並提示。
- WHEN 店長刪除作品圖片 THE SYSTEM SHALL 二次確認後同時刪除資料列與 Storage 檔案。如果
  Storage 檔案刪除失敗，資料列仍以刪除為準，檔案留下成為孤兒檔案，記為已知殘留。
- THE SYSTEM SHALL 在前台依上傳時間由新到舊，以三欄正方形格狀（仿 IG 個人頁）顯示作品集；
  點擊圖片可以放大檢視；作品集為空時顯示「尚無作品」的空狀態。

### 設計師請假

- WHEN 店長替某位設計師新增請假日 THE SYSTEM SHALL 只接受今天（含）以後的日期，並檢查
  該設計師當天是否已有有效預約（pending／confirmed）；如果有，顯示受影響預約清單警告
  （比照 `findAffectedAppointmentsForClosedDate`），店長確認後才寫入。
- WHEN 某位設計師在某天請假 THE SYSTEM SHALL 讓 `get_available_slots` 在指定該設計師時
  回傳空陣列；不指定時，不把他列入候選；`create_appointment` 拒絕該設計師當天的預約，
  沿用既有錯誤碼。
- WHEN 全店公休日（`closed_dates`）或每週固定公休 THE SYSTEM SHALL 對所有設計師都生效，
  和個人請假是疊加的關係，不互相覆蓋。

### 顧客端選擇設計師

- WHEN 顧客選完服務 THE SYSTEM SHALL 顯示設計師選擇步驟：第一個選項是「不指定設計師」，
  接著依 `sort_order` 列出有提供該服務的啟用中設計師，每張卡片顯示頭像、名字、專長標籤。
- WHEN 顧客點擊某位設計師的「詳細資訊」 THE SYSTEM SHALL 顯示詳細資訊面板（行動裝置用
  底部抽屜或全螢幕，最終版型交給 mockup 決定）：頭像、名字、專長標籤、簡介、IG 連結按鈕
  （有填 IG 帳號才顯示）、作品集九宮格；面板內可以直接選擇這位設計師。
- WHEN 顧客點擊 IG 連結 THE SYSTEM SHALL 在新分頁開啟 `https://www.instagram.com/<帳號>/`，
  並帶 `rel="noopener noreferrer"`。
- WHEN 顧客換了服務 THE SYSTEM SHALL 清除已經選的設計師與時段；如果原本的設計師也有提供
  新服務，保留選擇也可以，最終行為交給 mockup 決定，但不能保留一個不提供新服務的設計師。
- WHEN 顧客換了設計師 THE SYSTEM SHALL 清除已經選的時段，重新查詢可預約時段。

### 可預約時段與建立預約

- THE SYSTEM SHALL 在 `appointments` 新增 `designer_id`（必填，參照設計師表），並把 exclusion
  constraint 改成「同一個 `designer_id` 的有效預約時段不可重疊」。不同設計師的同一時段可以
  同時存在。
- WHEN 顧客指定設計師查詢可預約時段 THE SYSTEM SHALL 只用該設計師的既有預約（含各自服務的
  `buffer_minutes`）、請假日，加上全店營業時間、公休日、`booking_policy` 提前量、90 天視野
  計算。
- WHEN 顧客不指定設計師查詢可預約時段 THE SYSTEM SHALL 回傳「至少有一位符合條件的設計師
  有空」的時段聯集。符合條件是指：啟用中、有提供該服務、當天沒請假。回傳內容只包含時間，
  不透露是哪位設計師有空。
- WHEN 顧客指定設計師送出預約 THE SYSTEM SHALL 在交易內驗證該設計師符合條件、時段可用；
  如果與該設計師既有預約重疊，回傳既有的 `SLOT_CONFLICT`。
- WHEN 顧客不指定設計師送出預約 THE SYSTEM SHALL 在交易內從符合條件、而且該時段有空的
  設計師中，依下列順序指派一位：
  1. 當天（Asia/Taipei）有效預約筆數最少的設計師；
  2. 同分時取 `sort_order` 較小者；
  3. 再同分時取 `id` 較小者。
  如果因為併發導致第一順位的設計師已經被訂走，要嘗試下一位候選；全部都不行才回傳
  `SLOT_CONFLICT`。
- WHEN 預約建立成功 THE SYSTEM SHALL 回傳實際指派的設計師名稱，讓成功頁顯示。
- THE SYSTEM SHALL 讓 RPC 的設計師參數可以省略（預設為「不指定」），讓舊版前端在
  migration 套用後、新前端部署前，仍然可以正常預約（部署順序相容）。

### 後台預約管理

- THE SYSTEM SHALL 在後台週曆事件、列表、預約詳情 Modal 顯示設計師名稱，並提供設計師
  篩選（全部／單一設計師）；呈現方式交給 mockup 決定（例如依設計師上色）。
- WHEN 店長在後台改期 THE SYSTEM SHALL 只用**該預約原本設計師**的既有預約與請假日計算可選
  時段，送出時維持同一個 `designer_id`；與該設計師其他預約衝突時，回傳既有的
  `SLOT_CONFLICT` 錯誤處理。

### 通知信

- THE SYSTEM SHALL 在確認信、提醒信、取消信、改期信加入設計師名稱，設計師名稱要經過既有
  的 HTML 跳脫處理（比照 TASK-051 對顧客姓名的處理）。

### 升級與資料遷移

- WHEN 套用本 Epic 的 migration THE SYSTEM SHALL 建立一位「預設設計師」（名稱可以之後在
  後台修改），把**所有既有預約**都歸給他，並把**所有既有服務**都對他開啟。升級完成後，
  在店長新增其他設計師之前，前台行為（可預約時段、預約結果）與升級前一致。

## 資料與 API

以下是規格層級的假設，實際欄位名稱與 migration 拆分在架構規劃階段定案。

- 輸入（新增資料）：
  - `designers`：`id uuid`、`name text`、`bio text null`、`specialties text[]`（0～5 個）、
    `instagram_handle text null`（只存帳號名稱，不存網址）、`avatar_url text null`、
    `is_active boolean default true`、`sort_order int`、`created_at`。
  - `designer_services`：`designer_id`、`service_id`（複合主鍵）。有這一列代表該設計師提供
    這項服務。
  - `designer_leaves`：`designer_id`、`date`（複合主鍵），代表整天請假。
  - `designer_portfolio_images`：`id`、`designer_id`、`image_url`、`storage_path`、
    `created_at`。
  - `appointments.designer_id uuid not null references designers(id)`（先以 nullable 加入欄位、
    回填預設設計師後，再改成 `not null`）。
  - 新增 Storage bucket（暫定 `designer-assets`，public read，只有 `is_admin()` 能寫），
    路徑分 `avatar/` 與 `portfolio/<designer_id>/`。
- RPC 變更：
  - `get_available_slots(p_service_id, p_date, p_designer_id default null)`
  - `create_appointment(..., p_designer_id default null)`：回傳值加上指派到的設計師名稱。
  - exclusion constraint 改成 `exclude using gist (designer_id with =, tstzrange(...) with &&)`，
    需要 `btree_gist` 擴充套件（既有 migration 的註解已經預告這個需求）。
  - 前台設計師列表：讀取「啟用中、有提供指定服務」的設計師公開欄位（名稱、頭像、簡介、
    專長、IG 帳號、作品集）。要用 RLS 直接讀取還是包成 RPC，在架構規劃階段決定。
- 輸出：
  - 前台設計師資料只包含上面列的公開欄位，**不包含**請假日與任何預約資訊。
  - 不指定時的時段回傳格式與現行一致（只有 `start_at`／`end_at`）。
- 驗證：前端與資料庫（`check` constraint）都要驗證名稱長度、專長數量與長度、IG 帳號格式、
  作品集張數上限（張數上限至少要在資料庫層或 RPC 層有一道檢查，不能只靠前端）。
- 錯誤：沿用既有錯誤碼（`VALIDATION_ERROR`／`SLOT_CONFLICT` 等）與「不外洩原始錯誤」的慣例，
  不新增顧客可見的錯誤碼，除非架構規劃階段認為有必要。
- 受影響的既有程式（供架構規劃參考，不是完整清單）：`lib/booking/api.ts`、
  `app/_components/booking/*`、`lib/admin/appointments.ts`、`lib/admin/reschedule-slots.ts`
  （改期時段計算要過濾設計師）、`app/admin/_components/WeekCalendar.tsx`／
  `AppointmentListView.tsx`／`AppointmentDetailDialog.tsx`、`lib/email/templates/*`、
  `app/api/webhooks/appointment-events`、`app/api/cron/appointment-reminders`、
  `scripts/seed-booking-data.mjs`。

## 安全性與隱私

- 身分驗證：沿用既有的 `is_admin()` 加 authenticated 邊界（含 TASK-059 的 aal2 應用層檢查）。
  本 Epic 不新增任何登入身分。
- 權限：
  - `designers`／`designer_services`／`designer_portfolio_images`：anon 只能讀「公開欄位」，
    而且只能讀啟用中的設計師；只有 `is_admin()` 可以寫。
  - `designer_leaves`：anon **不能**直接讀（請假日屬於設計師個人行程），只透過
    `SECURITY DEFINER` RPC 間接影響時段計算；只有 `is_admin()` 可以讀寫。
  - 新資料表要在同一個 migration 寫出明確的最小權限 GRANT（見 `decisions.md` TASK-065）。
  - 新資料表與 `appointments` 都**不得**啟用 `force row level security`，理由與
    `booking_policy`／`closed_dates` 相同：RPC 內的檢查依賴讀得到資料列。
- 敏感資料：
  - 設計師的名字、頭像、IG 帳號、作品集是店家刻意公開的資訊。店長新增時，介面上應該讓
    店長知道這些資料會公開顯示。
  - 「不指定」時段查詢**不能**透露是哪位設計師有空、各設計師的預約數量，避免顧客推算出
    其他人的預約狀況。
- 濫用情境：
  - **IG 連結注入**：只存帳號名稱，由程式組出固定網域的網址，不接受任意 URL，杜絕
    `javascript:` 或釣魚網址。
  - **圖片網址竄改**：前台只渲染來自 `designer-assets` bucket 的網址（比照
    `resolveStoreDisplay`／`resolveAdminAvatarUrl` 的白名單）。
  - **上傳檔案**：限制 MIME 類型與大小，Storage policy 限制只有 `is_admin()` 可以寫入、
    覆寫、刪除。路徑由伺服器端或程式決定，不使用使用者提供的檔名。
  - **繞過前端直接呼叫 RPC**：`create_appointment` 必須在資料庫端重新驗證設計師啟用中、
    有提供該服務、當天沒請假；傳入停用、請假或不提供該服務的設計師 id 都要被拒絕。
  - **自動指派的併發**：兩位顧客同時對同一時段選「不指定」時，exclusion constraint 是最後
    防線，RPC 要能在第一順位衝突時改試下一位，而不是直接失敗；需要用併發整合測試驗證。
  - **既有規則共存**：設計師條件、請假日要和既有的公休日（TASK-028）、固定營業時間
    （TASK-062）、緩衝時間（TASK-024）、提前量（TASK-048）檢查同時生效，不能互相覆蓋
    或短路。

## 驗收標準

- 升級 migration 套用後，既有預約全部有 `designer_id`，既有服務都對預設設計師開啟；在新增
  其他設計師之前，`get_available_slots`／`create_appointment` 的結果與升級前一致（以既有
  整合測試全數通過作為證據）。
- 店長可以新增、編輯、停用、重新啟用設計師，可以設定頭像、簡介、專長、IG 帳號、提供的
  服務、作品集（最多 12 張）與整天請假日，所有欄位驗證都在前端與資料庫兩層生效。
- 兩位設計師都提供同一項服務時，同一個時段可以各自成立一筆預約；同一位設計師的同一個
  時段不能成立第二筆預約（資料庫層級保證）。
- 顧客選完服務後只看到有提供該服務的啟用中設計師，以及「不指定設計師」；詳細資訊面板
  正確顯示專長、IG 連結（新分頁、`noopener noreferrer`）與仿 IG 作品集。
- 指定設計師時，只顯示該設計師的空檔；不指定時，顯示所有符合條件設計師空檔的聯集，而且
  回應內容不包含設計師資訊。
- 不指定時，自動指派結果符合「當天預約數最少 → `sort_order` → `id`」的規則；併發情境下
  不會雙重預約，第一順位衝突時會改派給下一位有空的設計師。
- 設計師請假日、停用、未提供服務三種情況，透過直接呼叫 RPC 也無法成立預約。
- 後台週曆、列表、詳情都顯示設計師，可以依設計師篩選；改期只計算原本設計師的空檔。
- 四種通知信都顯示設計師名稱，名稱經過 HTML 跳脫。
- 沒有任何前台路徑可以讀到 `designer_leaves` 或其他設計師的預約資料。

## 驗證計畫

- 單元測試：專長、IG 帳號、名稱的驗證純函式；IG 網址組成；圖片網址白名單；自動指派的
  排序規則（如果有抽成純函式）；前台換服務、換設計師時的 state 重置；通知信範本加入設計師
  名稱與跳脫。
- 整合測試（真實 Supabase，新增獨立的 `vitest.designers.config.ts`，比照既有的分檔慣例）：
  - 不同設計師同時段可以並存，同一設計師同時段會被 exclusion constraint 拒絕。
  - 指定與不指定兩種 `get_available_slots` 的結果，並與公休日、固定公休、緩衝時間、提前量、
    請假日交叉驗證。
  - `create_appointment` 拒絕停用、請假、不提供該服務的設計師。
  - 自動指派規則，以及併發下的改派候選。
  - RLS 邊界：anon 讀不到 `designer_leaves`、讀不到停用設計師、不能寫任何設計師資料表；
    Storage 只有 admin 能寫。
  - 既有的 `test:booking`／`test:admin-booking`／`test:business-hours`／`test:rls`／
    `test:booking-policy`／`test:services`／`test:notifications` 全數回歸通過。
  - 注意：`appointments` 的 INSERT/UPDATE 有 Database Webhook trigger 會真的寄信，整合測試
    要沿用既有的防護做法，不能只靠 `vi.mock`。
- E2E：專案目前沒有 E2E 框架，本 Epic 不強制引入，改用瀏覽器手動走查加截圖替代（是否
  趁這個 Epic 引入 Playwright，在架構規劃階段再決定）。
- 視覺：設計師選擇步驟、詳細資訊面板（含作品集）、後台設計師管理頁、週曆篩選，在桌面與
  行動裝置寬度都截圖，並對照 `ai/checklists/design-review-checklist.md`。
- 手動：在 Vercel preview 或正式環境走一次「新增設計師 → 開服務 → 上傳作品 → 前台預約
  （指定與不指定各一次）→ 收確認信 → 後台週曆篩選 → 設定請假 → 確認時段消失」的完整
  流程。
