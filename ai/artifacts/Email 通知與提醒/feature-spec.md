# 功能規格書

## Metadata

- 功能：Email 通知與提醒（對應 `tools/kanban/epics.json` 已登記的同名 Epic）
- 負責人：待指定
- 狀態：草稿（待人工核准）
- 風險等級：高（首次在本專案引入第三方 Email 服務與對外 webhook／排程端點；端點若缺乏
  驗證機制可能被濫用大量寄信或觸發非預期的資料查詢，需架構、安全性、測試三方審查）
- 已與人工確認的範圍決策：
  - Email 發信服務商採用 **Resend**（`.env.example` 既有的 `EMAIL_API_KEY`／
    `EMAIL_FROM_ADDRESS` 佔位欄位沿用，文件補上明確對應 Resend）。
  - 「預約前寄送提醒信」採用 **Vercel Cron Jobs** 定時掃描，不引入 Supabase
    `pg_cron`／`pg_net` 等額外資料庫延伸套件。
  - 提醒信固定在預約時段前 **24 小時**寄出，本批次不提供設計師可調整的介面。
  - **（TASK-060 追加，2026-08-24）** 四種信件（確認／取消／改期／提醒）追加視覺
    優化：帶入 `store_settings.logo_url` 作為信頭 Logo（若店家尚未上傳，省略圖片
    區塊，不顯示預留位置）；信尾簽章統一改為「店名＋電話＋地址」，取代原本只有
    店名＋電話的 `contactLine`。四種信件共用同一套版型／簽章邏輯，需抽成共用
    函式供各範本呼叫，避免重複。

## 問題

- 顧客完成預約後，系統不會寄送任何確認信，顧客只能仰賴預約成功頁當下看到的資訊，事後
  無法從信箱找回預約細節。
- 顧客沒有任何預約提醒，若忘記時間可能無故爽約，對設計師排程造成影響。
- 設計師（或未來的顧客自助功能）取消／改期預約時，顧客不會收到任何通知，只能透過店家
  口頭告知。
- 本專案目前完全沒有串接任何第三方 Email 服務，也沒有任何定時任務機制。

## 使用者

- 顧客（前台，未登入）：間接受影響——完成預約、預約前 24 小時、預約被取消或改期時
  收到對應的 Email。
- 設計師：間接受影響——後台取消／改期預約的既有操作，現在會額外觸發顧客通知信；設計師
  不需要手動做任何寄信操作。

## 目標

- 顧客完成預約後，自動收到預約確認信，內容包含服務、日期時段、聯絡資訊摘要。
- 顧客的預約在開始前 24 小時，自動收到提醒信。
- 顧客的預約被取消或改期（不論是設計師在後台操作，或未來顧客自助功能觸發）時，自動
  收到對應的狀態通知信。
- 三種信件的觸發與寄送皆為系統自動完成，不需要設計師手動操作；寄信失敗不得阻擋或影響
  既有的預約／取消／改期操作本身成功與否。

## 非目標

- **Email 內容範本的視覺化編輯介面**——本批次信件內容為固定版型（依資料動態帶入服務、
  時間等欄位），設計師無法在後台自訂信件文案或版型，需要調整時由工程人員修改程式碼內的
  範本。
- **多語系信件**——維持全站繁體中文，不做信件多語言版本。
- **顧客自助查詢／取消預約連結**——確認信/提醒信本批次**不包含**指向「查看我的預約」
  頁面的連結（例如以 `appointments.access_token` 組成的網址），因為該頁面屬於「顧客
  自助查詢／取消預約」Epic（尚未開始），現在放連結會是死連結。待該 Epic 上線後，應
  回頭在信件範本補上此連結，屬於後續任務。
- **提醒時間可設定化**——已與人工確認，本批次固定 24 小時，不提供後台設定介面。
- **簡訊或其他通知管道**——只做 Email，不做 SMS／LINE 通知等其他管道。
- **寄送失敗的重試佇列／死信處理**——本批次採用 Resend API 呼叫本身的基本錯誤處理
  （失敗記錄 log，不建立自動重試機制或佇列系統），寄送失敗視為已知限制，不阻擋其他
  功能；未來如需更嚴謹的送達保證，屬於獨立的後續強化項目。
- **開信／點擊追蹤等行銷分析**——本批次信件皆為交易型通知信（transactional email），
  不整合任何行銷分析或追蹤像素。
- **取消訂閱機制**——因信件皆為顧客主動預約後才觸發的交易型通知，不提供也不需要
  「取消訂閱」連結（沿用一般交易型 Email 的既有慣例，非行銷信）。

## 使用者故事（User Stories）

| 故事 | 身為／我想要／以便 | 驗收標準 |
|---|---|---|
| 預約成立寄送確認信 | 身為顧客，我想要在完成預約後立即收到確認信，以便留存預約紀錄、確認資訊正確 | 顧客完成預約（`appointments` 新增一筆 `status='pending'` 資料列）後，系統自動觸發並寄出確認信至 `customer_email`（若有填寫）；信件內容含服務名稱、日期時段、聯絡資訊摘要；顧客未填寫 email 時不寄信，不視為錯誤；寄信失敗不影響預約本身已成立的結果 |
| 預約前寄送提醒信 | 身為顧客，我想要在預約時段前收到提醒信，以便不會忘記預約 | 系統於預約開始前 24 小時自動寄送提醒信至 `customer_email`（若有填寫）；同一筆預約只會收到一次提醒信，不重複寄送；已取消的預約不會收到提醒信 |
| 取消／改期時寄送通知信 | 身為顧客，我想要在預約被取消或改期時收到通知信，以便掌握最新的預約狀態 | 預約被取消（`status` 變更為 `cancelled`）時，系統自動寄送取消通知信；預約被改期（`start_at`／`end_at` 變更）時，系統自動寄送改期通知信，內容包含新的日期時段；顧客未填寫 email 時不寄信，不視為錯誤 |

## 使用者旅程

```text
身為顧客，
我在前台完成了一筆預約，以便之後能準時到店，也想在忘記時有個提醒。

我填完聯絡資訊送出預約，畫面顯示預約成功，幾分鐘內我的信箱收到一封確認信，寫著
「經典剪髮，8/20（三）14:00」。到了 8/19 下午 2 點（預約前 24 小時），我又收到一封
提醒信，內容跟確認信類似但標題是「提醒您明天有預約」。後來我打電話請設計師幫我改到
8/21，設計師在後台把我的預約改期，我隨即收到一封改期通知信，寫著新的時段。
```

## 功能需求

使用可測試的語言撰寫。

- WHEN `appointments` 新增一筆資料列（顧客完成預約） THE SYSTEM SHALL 觸發確認信寄送
  流程；若該筆資料的 `customer_email` 非空，呼叫 Resend API 寄送確認信；若
  `customer_email` 為空，不寄信，不記錄為錯誤。
- WHEN Vercel Cron 排程觸發（建議頻率：每小時或更高頻率，實作階段依 Resend
  用量與 Vercel 方案限制決定） THE SYSTEM SHALL 查詢 `start_at` 落在「現在起 24 小時
  後」附近時間窗、`status` 為 `pending` 或 `confirmed`、且尚未寄送過提醒信
  （`reminder_sent_at is null`）的預約，逐筆寄送提醒信並記錄 `reminder_sent_at`，
  避免重複寄送。
- WHEN `appointments.status` 變更為 `cancelled` THE SYSTEM SHALL 觸發取消通知信寄送
  流程；`customer_email` 非空時寄送，內容包含原預約的服務與時段資訊。
- WHEN `appointments.start_at`／`end_at` 因改期而變更（`status` 維持非 `cancelled`）
  THE SYSTEM SHALL 觸發改期通知信寄送流程；`customer_email` 非空時寄送，內容包含
  新的日期時段。
- WHEN Email 寄送呼叫失敗（Resend API 錯誤或逾時） THE SYSTEM SHALL 記錄錯誤（伺服器
  端 log），不影響觸發該次寄信的預約／取消／改期操作本身的成功結果，不對顧客顯示
  任何寄信失敗的訊息（顧客不需要知道通知信寄送的內部狀態）。
- WHEN 外部呼叫者對 webhook 或排程端點發出請求但未附帶正確的驗證密鑰 THE SYSTEM SHALL
  拒絕該請求（回傳 401／403），不執行任何查詢或寄信動作。

## 資料與 API

- 輸入：
  - `appointments` 新增欄位（新 migration）：
    - `reminder_sent_at timestamptz`（選填，`null` 代表尚未寄送過提醒信，避免重複
      寄送）
  - 環境變數（`.env.example` 更新，補上明確對應說明）：
    - `EMAIL_API_KEY`：Resend API Key。
    - `EMAIL_FROM_ADDRESS`：寄件人地址（需為已在 Resend 驗證過的網域）。
    - `SUPABASE_WEBHOOK_SECRET`（新增）：Supabase Database Webhook 呼叫時攜帶的共用
      密鑰，本專案的 webhook 端點用來驗證請求確實來自己方 Supabase 專案設定的
      Database Webhook，而非任意外部呼叫者。
    - `CRON_SECRET`（新增）：Vercel Cron 呼叫排程端點時攜帶的共用密鑰（Vercel Cron
      內建支援以 `Authorization` header 帶入此密鑰，比照 Vercel 官方建議做法）。
  - Supabase Database Webhook（新增設定，非程式碼）：於 `appointments` 表設定 `INSERT`
    與 `UPDATE` 事件的 webhook，指向本專案新增的 API Route（`/api/webhooks/
    appointment-events`），攜帶 `SUPABASE_WEBHOOK_SECRET` 於自訂 header。
  - Vercel Cron 設定（`vercel.json` 新增 `crons` 設定），定時呼叫
    `/api/cron/appointment-reminders`。
- 輸出：
  - 三個 API Route（`/api/webhooks/appointment-events`、`/api/cron/
    appointment-reminders`）皆只回傳成功/失敗狀態，不回傳任何預約細節內容給呼叫端
    （呼叫端是 Supabase／Vercel 系統本身，非使用者瀏覽器）。
- 驗證：
  - 兩個端點皆須驗證共用密鑰，缺少或不正確時一律拒絕（401），不執行任何後續邏輯。
  - Webhook payload 需驗證來自 `appointments` 表、事件類型（`INSERT`／`UPDATE`）與
    比對新舊資料（`old_record` vs `record`）判斷是取消還是改期。
- 錯誤：
  - Resend API 呼叫失敗時記錄 log（含預約 id、錯誤訊息，不記錄顧客 email 明文於一般
    log，比照個資保護原則），端點仍回傳成功狀態給 Supabase／Vercel（避免觸發不必要的
    webhook 重試風暴），除非是密鑰驗證失敗等呼叫本身有問題的情況才回傳錯誤狀態。

## 安全性與隱私

- 身分驗證：webhook／排程端點皆非使用者可存取的一般頁面或 API，透過共用密鑰
  （`SUPABASE_WEBHOOK_SECRET`／`CRON_SECRET`）驗證呼叫來源，不使用 Supabase Auth
  的使用者身分驗證機制（呼叫端不是登入使用者，是系統對系統）。
- 權限：兩個 API Route 需要用 `SUPABASE_SERVICE_ROLE_KEY`（既有環境變數，`TASK-002`
  已建立）查詢 `appointments`（略過 RLS，因為 anon 對 `appointments` 本來就沒有直接
  讀取權限，系統內部流程需要完整讀取權限才能組成通知信內容），service role key
  只在這兩個伺服器端 API Route 內使用，不暴露給前端。
- 敏感資料：Email 地址與姓名為顧客個資，寄信內容需避免在一般應用程式 log 中明文記錄
  完整 email／電話；Resend API 呼叫本身透過 HTTPS，符合既有的傳輸加密慣例。
- 濫用情境：
  - 若共用密鑰外洩，攻擊者可能觸發大量寄信（耗盡 Resend 額度／騷擾顧客）或觸發不必要
    的資料庫查詢；密鑰需妥善保存於 Vercel／Supabase 專案的環境變數設定，不得記錄於
    程式碼或版控。
  - webhook 端點需驗證 payload 結構符合預期（`appointments` 表、預期的欄位），避免
    格式不符時因未預期的資料形狀導致例外或誤發信件。
  - 排程端點的查詢範圍需限定在「時間窗＋未寄送過提醒」的條件內，避免邏輯錯誤導致
    對整個 `appointments` 表重複寄送。

## 驗收標準

- 顧客完成預約（且有填寫 email）後，於合理時間內收到確認信，內容正確。
- 顧客的預約於開始前 24 小時收到提醒信，且同一筆預約不會收到兩次提醒信。
- 顧客的預約被取消或改期後，收到對應的通知信，內容正確反映最新狀態。
- 顧客未填寫 email 的預約，上述三種情境皆不寄信，也不產生錯誤或阻擋原本操作。
- webhook／排程端點皆需要正確的共用密鑰才能觸發，未帶密鑰或密鑰錯誤時一律拒絕。
- Email 寄送失敗不影響預約／取消／改期操作本身的既有成功結果（無回歸）。
- 既有測試（`test:rls`／`test:booking`／`test:admin-booking`／`test:business-hours`／
  `test:store-settings`／`test:services`／`test:booking-policy`，視當時已完成的 Epic
  而定）重跑無回歸。

## 驗證計畫

- 單元測試：Email 內容組成的純函式（依預約資料組出信件標題／內容文字，含服務、時間
  格式化）；webhook payload 判斷是取消還是改期的純函式邏輯。
- 整合測試：對真實 Supabase 專案／測試環境驗證：webhook 端點在正確/錯誤密鑰下的
  行為；建立測試預約後確認 webhook 觸發並記錄呼叫（可用 mock Resend API 或測試模式
  API key，避免整合測試實際寄出大量真實信件）；排程端點的查詢邏輯對「時間窗內／外」
  「已寄過提醒／未寄過」預約的正確篩選。
- E2E：不適用傳統 UI E2E（本 Epic 無 UI），改以「建立測試預約→確認 webhook 被觸發→
  確認 Resend API 呼叫參數正確」的端到端流程驗證取代。
- 視覺：不適用（無 UI 變更）。
- 手動：至少一次使用真實（或測試模式）Resend API key，實際觸發一封確認信、一封提醒信
  （可用手動調整測試預約的 `start_at` 或直接呼叫排程端點模擬時間窗）、一封取消/改期
  通知信，確認信件實際送達且內容正確。
